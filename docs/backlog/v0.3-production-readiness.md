# v0.3 Production Readiness Backlog

This backlog records the production-readiness hardening tickets that must be resolved before calling the `v0.3` RCA contract stable.

The foundation work in [v0.3 Foundation Issues](v0.3-foundation-issues.md) established the first canonical path:

```text
RiskRule
-> InvestigationRequest
-> normalized observations
-> provider-neutral RCA
-> heuristic verification
-> optional materialized RiskSignal
```

This document tracks the next gate: making that path dependable under repeated reconcile, partial evidence, provider retries, status conflicts, bounded storage, and security constraints.

## Current Status

```text
v0.3 foundation contract: PARTIAL IMPLEMENTED
production-readiness contract: PLANNED
schema freeze: NOT READY
```

Implemented foundations:

- normalized observation contract
- structured `InvestigationRequest.status` compatibility fields
- basic heuristic claim verifier
- `RiskRule.spec.investigationPolicy` with `DirectRiskSignal` and `CreateRequest`
- `InvestigationRequest.status.lineage`

Not yet production-ready:

- formal terminal status semantics
- durable provider result checkpointing
- execution / attempt / provider request identity split
- evidence size and status budget limits
- canonical digest versioning
- evidence retention and payload reference security
- loop prevention policy enforcement
- datasource network and query safety policies
- provider data policy
- required evidence profiles and `NoIssueFound` gate
- low-cardinality metrics

## P0-1: Formal Status Semantics

Define the status dimensions without mixing workflow lifecycle and RCA conclusion.

Required split:

```yaml
status:
  phase: Completed
  outcome: Confirmed
  failure: null
  degradation:
    degraded: false
  conditions: []
```

Target fields:

| Field | Purpose |
| --- | --- |
| `phase` | Workflow lifecycle. |
| `outcome` | RCA conclusion. |
| `failure` | Workflow failure details when the workflow cannot complete. |
| `degradation` | Capability loss during execution. |
| `conditions` | Stage health and readiness. |

Candidate `phase` values:

```text
Pending
Collecting
Reasoning
Verifying
Completed
Failed
```

Candidate `outcome` values:

```text
Confirmed
Inconclusive
NoIssueFound
Unknown
```

`ExecutionFailed` should not be an RCA outcome. Workflow failures should be represented through `status.phase=Failed`, `status.outcome=Unknown`, and `status.failure`.

Acceptance:

- `outcome` only describes RCA conclusions.
- `phase` only describes workflow lifecycle.
- `Observed` is replaced or explicitly deprecated.
- `ExecutionFailed` is removed from the target RCA outcome enum.
- `status.failure` includes `code`, `message`, `stage`, and `retryable`.
- documentation lists legal terminal combinations:
  - `Completed + Confirmed`
  - `Completed + Inconclusive`
  - `Completed + NoIssueFound`
  - `Failed + Unknown + failure`
- tests cover success, inconclusive, no issue found, and failed execution paths.

## P0-2: Durable Provider Execution Checkpoint

Prevent repeated hosted-provider calls when reconciliation or status persistence is retried.

Problem:

```text
provider call succeeds
-> status patch conflicts
-> provider result is not durable
-> next reconcile calls provider again
```

Target checkpoint:

```yaml
status:
  execution:
    id: sha256:...
    state: ProviderCompleted
    providerResult:
      digest: sha256:...
      result: {}
```

Acceptance:

- `ProviderCompleted` is set only after the normalized provider result is durably persisted.
- same completed `execution.id` reuses the persisted result.
- verifier can rerun from the persisted provider result without another provider call.
- status conflict retry does not rerun external provider side effects.
- tests simulate provider success followed by status update conflict.
- docs state that `InvestigationRun` is a possible future child resource, but not required for the first v0.3 hardening cut.

## P0-3: Execution / Attempt / Provider Request Identity

Separate logical execution identity from retry attempts and provider-side request identity.

Target model:

```yaml
execution:
  id: sha256:logical-execution
  attempts:
    - id: attempt-001
      providerRequestID: req_xxx
      result: TimedOut
    - id: attempt-002
      providerRequestID: req_yyy
      result: Completed
```

Definitions:

| Identity | Meaning |
| --- | --- |
| `execution.id` | Logical input identity. |
| `attempt.id` | One FluxAgent attempt for the logical execution. |
| `providerRequestID` | Provider-side request ID when available. |

Acceptance:

- `execution.id` is derived from request UID, observed generation, evidence bundle digest, provider generation, and reasoning policy version.
- same completed `execution.id` reuses the persisted result.
- same `execution.id` with incomplete attempts follows retry policy.
- provider request IDs are stored when adapters expose them.
- docs state that hosted LLMs do not guarantee deterministic output for identical logical input.

## P0-4: Evidence Size Limits And Status Budget

Bound CRD status size and avoid storing large observability payloads in Kubernetes objects.

Acceptance:

- define `maxEvidenceRefs`
- define `maxClaims`
- define `maxSummaryBytes`
- define `maxStatusBytes`
- truncate evidence summaries and claim text when needed
- record `truncated`, `originalCount`, and `retainedCount`
- tests cover large log and event evidence
- docs state that CRD status stores compact metadata, not full logs or timeseries

## P0-5: Canonical Digest Contract

Make query, content, evidence bundle, and fingerprint digests stable across serialization differences.

Target canonicalization:

```text
fluxagent-observation-json-v1
```

Acceptance:

- object keys are sorted
- set-like arrays are sorted
- timestamps are UTC with defined precision
- floating-point values have stable representation
- non-semantic fields are excluded
- Unicode normalization is defined
- digest records include algorithm and canonicalization version
- golden tests cover map order, timestamp precision, array order, and equivalent payloads

## P0-6: Evidence Retention And PayloadRef Security

Define the opt-in external evidence retention contract before implementing raw or normalized snapshots.

Retention modes:

```text
MetadataOnly
NormalizedSnapshot
RawSnapshot
```

Target spec:

```yaml
spec:
  evidenceRetention:
    mode: NormalizedSnapshot
    retention: 168h
    storageRef:
      name: evidence-s3
    encryption:
      required: true
    deletionPolicy: Delete
    accessPolicy:
      namespaceScoped: true
```

Target status reference:

```yaml
payloadRef:
  scheme: s3
  digest: sha256:...
  encrypted: true
  expiresAt: ...
  retentionClass: incident-7d
```

Acceptance:

- external evidence storage remains disabled by default
- raw snapshots require explicit opt-in
- storage contract covers encryption, access control, tenant isolation, deletion, lifecycle, payload integrity, and credential rotation
- deleting an `InvestigationRequest` has defined evidence deletion behavior
- docs distinguish fixture replay from production incident replay

## P0-7: Finding Identity And Incident Occurrence

Avoid fingerprints that are either too broad or too narrow.

Target identities:

```text
objectFindingIdentity
logicalFindingIdentity
incidentOccurrence
```

Identity inputs:

| Identity | Inputs | Purpose |
| --- | --- | --- |
| `objectFindingIdentity` | source UID, target UID, finding type, normalized attributes | precise dedup |
| `logicalFindingIdentity` | apiVersion, kind, namespace, name, finding type, normalized attributes | dashboard and long-term correlation |
| `incidentOccurrence` | finding identity, observed generation, rounded evidence window | per-incident object identity |

Acceptance:

- namespace/name and object UID are both recorded
- cooldown is a matching policy, not a fingerprint input
- fingerprint schema version is recorded
- tests cover same workload name with different UID
- tests cover same UID with different generation or evidence window

## P0-8: Loop Prevention Policy

Prevent `RiskSignal -> InvestigationRequest -> RiskSignal` loops.

Acceptance:

- controller checks lineage, source UID, investigation depth, and policy
- annotation is not the only loop-prevention signal
- default policy does not reinvestigate discovered signals
- maximum investigation depth is enforced by controller
- tests cover missing annotation but preserved lineage
- tests cover depth limit

## P0-9: DataSource Network Safety Policy

Prevent SSRF while still allowing legitimate cluster-private observability endpoints.

Rules:

- metadata endpoints are always denied
- loopback and link-local addresses are denied by default
- private networks are allowed only by allowlist or namespace policy
- public endpoints are governed by datasource and provider data policy
- redirects are revalidated after DNS and IP resolution

Target policy:

```yaml
networkPolicy:
  allowedHosts:
    - "*.monitoring.svc.cluster.local"
    - "*.logging.svc.cluster.local"
  allowedCIDRs:
    - 10.32.0.0/16
  deniedCIDRs:
    - 169.254.169.254/32
```

Acceptance:

- tests reject metadata endpoint access
- tests reject redirect-to-metadata
- tests allow configured cluster service endpoints
- HTTP clients enforce timeout and maximum response size

## P0-10: Query Budget Policy

Protect Prometheus, Loki, and FluxAgent from expensive user-configured queries.

Policy is split into two layers:

Pre-query policy:

- max time range
- query syntax policy
- allowed functions
- regex restrictions
- timeout

Post-query enforcement:

- max series
- max samples
- max log lines
- oversized payload truncation or rejection

Acceptance:

- policy records truncation reason
- evidence records `originalCount` and `retainedCount`
- tests cover query range rejection
- tests cover oversized response truncation
- docs do not imply every backend can know `maxSeries` before query execution

## P0-11: Provider Data Boundary

Make hosted provider data transmission explicit and policy-controlled.

Target policy:

```yaml
spec:
  dataPolicy:
    allowExternalTransmission: true
    allowedEvidenceKinds:
      - MetricObservation
      - KubernetesEventObservation
    allowLogSamples: false
    maximumClassification: Internal
```

Acceptance:

- `ModelProvider.spec.dataPolicy` is defined
- hosted provider calls are blocked when external transmission is false
- heuristic-only mode remains fully usable
- log samples can be disabled independently from metrics and events
- docs state that read-only means read-only against user workloads, not zero data egress

## P0-12: Verifier Independence And Evidence Links

Make claim verification more than another copy of the same heuristic.

Verifier levels:

```text
L1 schema verifier
L2 evidence verifier
L3 domain verifier
```

Target evidence link:

```yaml
evidenceLinks:
  - evidenceRef: evidence-001
    role: Supports
    strength: Direct
```

Acceptance:

- claims support `Supported`, `Inferred`, `Unsupported`, `Contradicted`, and `Unverified`
- evidence links include role and strength
- verifier can only keep or lower confidence
- domain-specific support requirements are defined for OOMKilled, CrashLoopBackOff, ImagePullBackOff, and LatencyRegression
- tests cover irrelevant evidence, contradictory evidence, and temporal mismatch

## P0-13: Required Evidence Profiles And NoIssueFound Gate

Prevent false confidence when evidence is incomplete.

Target profile:

```yaml
evidenceRequirements:
  profile: RolloutLatencyRegression
  required:
    - capability: prometheus.query
      observationType: LatencyRatio
    - capability: kubernetes.workloads.read
      observationType: RolloutTimeline
  optional:
    - capability: loki.query
      observationType: TimeoutPattern
```

Acceptance:

- `NoIssueFound` is only allowed when required evidence is complete
- incomplete required evidence produces `Inconclusive`
- profiles are type-specific
- tests cover ImagePullBackOff and LatencyRegression with different required sources

## P0-15: RCA Quality Metrics

Add observability without creating high-cardinality metrics.

Allowed Prometheus label examples:

- `provider_type`
- `result`
- `namespace`
- `root_cause_type`
- `verification_status`

High-cardinality values must go to structured logs or traces only:

- execution ID
- request UID
- finding fingerprint
- digest values

Required metrics:

- `investigation_total`
- `provider_requests_total`
- `provider_failures_total`
- `datasource_query_duration_seconds`
- `evidence_truncated_total`
- `claim_verification_total`
- `deduplication_hits_total`
- `loop_prevention_total`
- `status_update_conflicts_total`
- `queue_depth`

Acceptance:

- raw evidence is never logged
- API keys and secret values are never logged
- tests or lint checks prevent high-cardinality labels where practical
- docs list allowed labels and structured log fields
