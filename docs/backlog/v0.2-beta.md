## Provider Response Governance Hardening

Status: first hardening batch complete on `main` after `v0.2.0-alpha.2`.

Goal:

- validate hosted provider responses before persisting RCA fields
- make malformed, incomplete, or non-JSON responses produce clear degraded conditions
- keep provider output execution-blind and read-only

Acceptance:

- tests cover malformed JSON, missing required fields, empty response bodies, and unsupported response shapes
- `RCAReady=False` exposes a stable reason such as `InvalidProviderResponse`
- no raw provider payload or secret material is persisted into CRD status

Completed:

- hosted provider structured responses reject missing `confidenceScore`
- structured responses reject empty or missing `rcaCauses`
- reasoning engine validates all provider `ModelResponse` values before deriving RCA fields
- tests cover incomplete hosted OpenAI content and invalid custom provider responses

Remaining:

- extend adapter tests for empty hosted-provider response bodies across OpenAI, Claude, and Gemini
- add broader malformed response-shape matrix per hosted provider
- review CRD status messages for provider payload truncation and secret safety

## Adapter Auth, Retry, And Backoff Hardening

Status: first hardening batch complete on `main` after `v0.2.0-alpha.2`.

Goal:

- standardize auth, timeout, retry, and backoff behavior across datasource adapters
- make optional integration failures visible without crashing reconciliation

Acceptance:

- Prometheus and Loki adapters have explicit timeout and retry behavior
- auth and connectivity failures map to stable degraded reasons
- tests cover transient failures, permanent auth failures, and partial-evidence behavior

Completed:

- Prometheus and Loki query paths share datasource retry and HTTP status classification
- transient 5xx and rate-limit responses retry before surfacing failure
- 401/403 responses map to `DatasourceAuthFailed`
- 429 responses map to `DatasourceRateLimited`
- malformed or unsuccessful datasource payloads map to `InvalidDatasourceResponse`
- `InvestigationRequest` evidence collection preserves typed datasource failure reasons in status
- `RiskRule` evaluation preserves typed datasource query failure reasons in `Ready`, `Degraded`, and generated `RiskSignal` evidence conditions
- background detection can still produce partial-evidence `RiskSignal` objects when another optional datasource query fails
- tests cover Prometheus transient retry, auth failure, invalid payload, Loki transient retry, rate limit, invalid payload, and investigation reason propagation
- tests cover `RiskRule` partial evidence with `DatasourceAuthFailed`
- post-hardening gates passed on current `main`: `make verify-v0.2-alpha`, `make verify-e2e-kind`, and `make verify-investigation-kind`
- tests cover datasource transport retry, canceled request handling, and timeout retry exhaustion

Remaining:

- review broader partial-evidence behavior for mixed datasource success/failure in background detection

## v0.2 Beta Release Gate Definition

Status: beta candidate gate passed on 2026-07-23 for current `main`.

Goal:

- define the minimum validation and documentation bar for `v0.2.0-beta.1`

Acceptance:

- release gate lists required local, kustomize, and kind validations
- non-goals remain explicit around autonomous remediation
- release notes and checkpoint use the same product status language
- beta claims do not exceed verified behavior

Required validation commands:

```sh
make verify-v0.2-alpha
make verify-e2e-kind
make verify-investigation-kind
kind get clusters
git status --short --branch
```

`make verify-v0.2-alpha` is the local and manifest baseline. It must pass:

- `go test ./...`
- `kubectl kustomize config/default`
- `kubectl kustomize examples/kind`

`make verify-e2e-kind` must pass and continue to cover:

- read-only `RiskRule -> RiskSignal` flow
- webhook notification delivery
- missing datasource degradation
- datasource capability mismatch degradation
- hosted provider auth failure degradation
- kind cluster cleanup for `fluxagent-demo`

`make verify-investigation-kind` must pass and continue to cover:

- `InvestigationRequest -> RCA` completion
- optional `InvestigationRequest -> RiskSignal` promotion
- missing datasource, capability mismatch, missing provider, provider auth failure, and provider rate-limit degradation
- kind cluster cleanup for `fluxagent-demo`

Required documentation checks:

- `docs/release-checkpoint.md` uses the same product status language as the beta release notes
- beta release notes list the exact commands above and their observed results
- release notes state that remediation remains guarded and secondary
- release notes state that OpenTelemetry and CloudWatch are not production-ready datasource paths
- adapter docs do not imply production readiness beyond Prometheus, Loki, Kubernetes Events, and currently wired hosted model provider behavior

Release non-goals:

- autonomous remediation as the default product path
- production-grade GitOps PR backend coverage
- production-grade CloudWatch or OpenTelemetry support
- multi-cluster policy hardening
- provider-complete or vendor-complete RCA coverage

Tagging rule:

- do not cut `v0.2.0-beta.1` unless the required validation commands pass on a clean branch synchronized with `origin/main`
- do not cut `v0.2.0-beta.1` unless the checkpoint and beta release notes describe the project as a read-only RCA beta, not a production remediation platform
- if any kind gate fails, keep the release notes as draft-only and record the failure in this backlog before retrying
