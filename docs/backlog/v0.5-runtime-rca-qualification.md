# v0.5 Runtime RCA Qualification Contracts

Status: `Active`

Contract versions:

- `v0.5-runtime-rca-matrix/v1`
- `v0.5-safe-remediation-matrix/v1`

## Scope-control rule

`v0.5-alpha.1` does not expand the Kubernetes detection domain. The release
must first prove that the existing bounded replay scenarios remain coherent
through the real controller, CRD, evidence, and User-facing Report paths.

> **No new detection domains until existing replay coverage is proven through
> user-facing runtime scenarios.**

This qualification is about runtime credibility, not about increasing the
number of detection patterns. Node, CNI, storage, Ingress, NetworkPolicy, and
cross-service dependency-graph scenarios remain outside this gate.

## 1. Runtime RCA matrix: `v0.5-runtime-rca-matrix/v1`

The matrix contains five bounded RCA cases. CrashLoopBackOff and high HTTP
error rate each have a positive and a negative evidence variant, for seven
runtime rows in total.

Every row must assert all of the following:

| Contract surface | Required assertion |
| --- | --- |
| `InvestigationRequest` | `status.phase` and `status.outcome` |
| RCA verdict | `status.verdict.rootCauseType` and `status.verdict.rootCauseEntity` |
| Evidence | `status.evidenceRefs[].source`, kind, stable ID, and referenced claim evidence |
| Risk projection | expected `RiskSignal` existence/absence, phase, projection reference, and bounded RCA fields |
| Failure semantics | `status.failure.code` when phase is `Failed`; missing-evidence and degradation semantics when applicable |
| Side effects | no `RemediationPlan`, `AgentAction`, or target mutation unless the case explicitly permits it |

The test must also verify that the User-facing report contains only objects
and fields available through the public FluxSeer API/CLI path. Internal
assertions are recorded separately in `fluxseer-test-report/v1`.

### Positive cases

| Case ID | Runtime trigger and required evidence | Expected product contract | Maximum supported claim |
| --- | --- | --- | --- |
| `service-port-mismatch` | Service `port`/`targetPort` does not resolve to the workload/container listener; Service and workload evidence are both present | `InvestigationRequest=Completed/Confirmed`; `rootCauseType=ServicePortMismatch`; root cause entity is the affected Service; projected `RiskSignal=Confirmed`; no remediation resources | The named Service route cannot reach the declared workload listener because of the observed port mismatch |
| `failed-scheduling` | `FailedScheduling` event with one bounded predicate, initially `InsufficientMemory` or an untolerated taint | `InvestigationRequest=Completed/Confirmed`; `rootCauseType=SchedulingFailure`; root cause entity is the Pending Pod; projected `RiskSignal=Confirmed`; no remediation resources | The target Pod cannot be scheduled because the selected scheduler predicate is evidenced |
| `probe-failure` | Readiness/liveness probe failure plus deterministic endpoint, configuration, or event evidence that supports the bounded probe claim | `InvestigationRequest=Completed/Confirmed`; `rootCauseType=ProbeFailure`; root cause entity is the affected workload/Pod; projected `RiskSignal=Confirmed`; no remediation resources | The selected probe is failing for the evidenced target; do not claim the underlying application defect unless separately evidenced |
| `crashloopbackoff-with-evidence` | CrashLoopBackOff/restart evidence plus deterministic application log or termination evidence | `InvestigationRequest=Completed/Confirmed`; bounded `rootCauseType` and entity supported by the application evidence; projected `RiskSignal=Confirmed`; no remediation resources | The named application/container failure supported by the declared evidence |
| `high-http-error-rate-with-causal-evidence` | Prometheus HTTP 5xx anomaly plus Loki or declared causal evidence; dependency identity is retained only when the evidence names it | `InvestigationRequest=Completed/Confirmed`; `rootCauseType=HighHTTPErrorRate`; root cause entity is the affected workload; projected `RiskSignal=Confirmed`; no remediation resources | The workload has a confirmed high HTTP error-rate incident linked to the declared causal evidence; do not infer an unobserved database, dependency, or application cause |

`ServicePortMismatch` is the public scenario/root-cause contract. Any legacy
internal coarse label such as `ConfigurationMismatch` must not cause the
User-facing report to lose the more specific public contract.

### Negative evidence cases

| Case ID | Observed symptom | Expected product contract | Forbidden result |
| --- | --- | --- | --- |
| `crashloopbackoff-without-causal-evidence` | CrashLoopBackOff/restart evidence is queryable, but no application or termination evidence supports a cause | Detection is retained; `InvestigationRequest=Completed/Inconclusive`; no confirmed root cause type/entity; no investigation-projected `RiskSignal`; no remediation resources | Fabricated application failure, database failure, or dependency failure |
| `high-http-error-rate-without-causal-evidence` | Prometheus shows elevated 5xx, but no causal log/event evidence is available | `InvestigationRequest=Completed/Inconclusive`; no confirmed causal root cause; no investigation-projected `RiskSignal`; no remediation resources | `5xx` alone becoming `DatabaseFailure`, `DependencyFailure`, or an application-specific root cause |

The matrix must distinguish an insufficient result from an execution failure:

```text
Evidence queried successfully but insufficient
    -> Completed / Inconclusive

Required datasource unavailable or query failed
    -> Failed / Unknown
       status.failure.code = explicit datasource/query failure reason

Symptom observed without causal evidence
    -> no Confirmed root cause

Investigation projection
    -> Confirmed only
       Inconclusive / NoIssueFound / Failed do not create a public RiskSignal
```

For a failed query, the runtime report must preserve the explicit failure
reason, such as `DatasourceQueryFailed`, rather than silently converting an
infrastructure failure into `Inconclusive`.

## 2. Safe remediation matrix: `v0.5-safe-remediation-matrix/v1`

The remediation matrix is separate from the RCA matrix. Its reference action
is the allowlisted `kubernetes.rolloutRestart` path after the normal
Plan -> Approval -> AgentAction sequence.

Global invariant:

```text
ExecutionSucceeded != EffectivenessEffective
```

Every row must assert the action approval lineage, exactly-once dispatch
identity, target mutation, verification request correlation, settling and
observation windows, and final effectiveness status.

| Case ID | Required sequence | Expected `AgentAction` contract | Forbidden result |
| --- | --- | --- | --- |
| `rolloutRestart-effective` | Target unhealthy; approved restart succeeds; original anomaly clears and health improves after observation | `status.execution.phase=Succeeded`; `status.effectiveness.phase=Completed`; `status.effectiveness.outcome=Effective`; verification is completed and correlated to execution/baseline | Treating API success alone as proof of recovery |
| `rolloutRestart-ineffective` | Target unhealthy; approved restart succeeds; original anomaly persists after observation | `status.execution.phase=Succeeded`; `status.effectiveness.phase=Completed`; `status.effectiveness.outcome=Ineffective`; post-action health is persisted | Reporting `Effective` because the mutation API returned success |
| `rolloutRestart-inconclusive` | Target mutation succeeds, but verification evidence is insufficient or conflicting | `status.execution.phase=Succeeded`; `status.effectiveness.phase=Completed`; `status.effectiveness.outcome=Inconclusive`; verification limitation is preserved | Rewriting execution to `Failed` or claiming `Effective` without verification |

No remediation matrix case may create an additional action, widen the target,
or bypass the approval and action-digest boundary. The read-only RCA cases in
the runtime RCA matrix must create zero `RemediationPlan` and zero
`AgentAction` objects.

## 3. Public report contract

The two report surfaces have different owners and audiences:

| Surface | Contract | Purpose |
| --- | --- | --- |
| Internal runtime report | `fluxseer-test-report/v1` | Test evidence: expected/actual values, assertions, differences, and side-effect checks |
| User-facing public report | `fluxseer-riskrule-report/v1` | Product output: public `RiskRule`, `InvestigationRequest`, linked/direct `RiskSignal`, evidence references, verdict, and conditions |

The internal runtime report proves whether the product followed the contract.
The User-facing report is the product contract consumed through the FluxSeer
API/CLI, for example `fluxseer report riskrule ...`.

Public coverage rules:

1. Count a scenario as public runtime coverage only when a user can retrieve
   its report through the supported API/CLI path with the required RBAC.
2. The public report must reflect the actual Kubernetes resources and status
   fields visible to that user; it must not inject test expectations or PASS/
   FAIL assertions.
3. Synthetic fixtures, fake-provider output, controller debug snapshots, and
   internal replay reports remain validation evidence and must not increase the
   public capability count.
4. A public report must preserve evidence source, stable evidence reference,
   verdict, root-cause entity, conditions, and explicit failure/missing-evidence
   semantics.

The five scenario names in the matrix are not automatically five public
capabilities. They become public coverage only after their runtime report
contract is exercised and stored as a retrievable product-output example.

## 4. Global acceptance invariants

These invariants are mandatory harness assertions for every matrix row:

```text
No fabricated root cause.
No unauthorized remediation side effect.
No internal-only evidence may be presented as a public runtime capability.
```

The `v0.5-alpha.1` qualification is complete only when all seven RCA rows and
all three remediation rows have runtime evidence, public/internal report
separation, explicit failure semantics, and zero unexpected side effects.

Completion of this document does not claim that the runtime qualification has
passed. It defines the acceptance contract that subsequent implementation and
test commits must satisfy.
