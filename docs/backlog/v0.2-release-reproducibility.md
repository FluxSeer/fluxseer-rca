## Artifact Identity

Goal:

- make every release artifact traceable to the same Git commit
- remove `latest` as a release source of truth
- make image tag human-readable and image digest authoritative

Required release identity:

```text
tag commit
= embedded Git revision
= OCI revision label
= release notes commit
= chart appVersion
= manifests image version
= published image source commit
```

Required image reference shape:

```yaml
image:
  repository: ghcr.io/fluxseer/fluxagent
  tag: v0.2.0-beta.1
  digest: sha256:...
```

Acceptance:

- Makefile build targets accept `VERSION`, `GIT_COMMIT`, and image repository variables
- release-managed manifests can use immutable digest references
- kind release verification can run against the intended release image reference
- `latest` is not used by release-managed paths
- demo-only use of `latest`, if retained, is documented as local-only and excluded from release verification

Planned verification target:

```sh
make verify-no-latest
```

## Binary And OCI Metadata

Goal:

- expose binary version metadata
- write OCI labels tying the container image to the source commit

Required binary metadata:

```text
Version: v0.2.0-beta.1
GitCommit: <full SHA>
BuildDate: <stable timestamp>
Dirty: false
```

Required OCI labels:

```text
org.opencontainers.image.title=FluxAgent
org.opencontainers.image.version=v0.2.0-beta.1
org.opencontainers.image.revision=<full SHA>
org.opencontainers.image.source=<source URL>
```

Acceptance:

- `fluxagent version` or equivalent command prints version, Git commit, build date, and dirty state
- operator image includes OCI version and revision labels
- demo-observability image includes OCI version and revision labels or is explicitly marked demo-only
- version metadata is injected through deterministic build inputs, not guessed implicitly by the Go toolchain

Planned verification target:

```sh
make verify-image-metadata
```

## Build Reproducibility

Goal:

- identify and reduce sources of image digest drift
- make release builds reproducible enough for beta release claims

Known drift from the freeze pass:

- two local rebuilds of `fluxagent/operator:latest` produced different image digests
- two local rebuilds of `fluxagent/demo-observability:latest` produced different image digests
- built images had no labels tying them to the Git commit

Potential drift sources:

- image created timestamp
- OCI provenance or attestation metadata
- Go build path
- Go build ID
- VCS metadata auto-detection
- base image tag drift
- copied file mtimes
- architecture mismatch
- dynamic build context files

Required build constraints:

- base images use digest-pinned references
- Go builds use `-trimpath`
- release build platform is explicit
- build timestamp uses commit timestamp or `SOURCE_DATE_EPOCH`, not wall-clock time
- dependencies remain locked by `go.sum`
- nonessential dynamic files are excluded from release build context

Acceptance:

- reproducibility verification compares two release image builds from the same commit
- image inspect and history differences are understood or eliminated
- remaining nondeterminism is documented before beta tag

Planned verification target:

```sh
make verify-reproducible-image
```

## Packaging Consistency

Goal:

- make Kustomize, Helm, image metadata, and release notes agree on version and commit

Required alignment for `v0.2.0-beta.1`:

- `charts/kube-ai-sre/Chart.yaml` `version: 0.2.0-beta.1`
- `charts/kube-ai-sre/Chart.yaml` `appVersion: "v0.2.0-beta.1"`
- Helm default image reference is not `latest`
- Kustomize release path can reference the intended image tag or digest
- release notes name the same verified commit as the release artifact source

Acceptance:

- Helm chart version and appVersion match release scope
- release-managed manifests do not use `latest`
- Helm is either included in the beta release gate or explicitly documented as out of scope

Planned verification target:

```sh
make verify-helm-version
```

## Lifecycle Smoke Test

Goal:

- verify install, upgrade, and uninstall behavior before beta tag
- make CRD retention behavior explicit

Minimum lifecycle gate:

```text
Fresh install
-> controller Ready
-> sample RiskRule / InvestigationRequest succeeds
-> Helm or Kustomize upgrade
-> existing CRs remain healthy
-> controller Ready again
-> uninstall
-> namespaced resources removed
-> CRD retention policy verified
-> no remaining kind cluster
```

CRD uninstall policy:

- ordinary uninstall should not accidentally delete user custom resources
- if CRD deletion is supported, it should require an explicit cleanup command or documented manual step
- release notes must state whether CRDs are retained or removed during uninstall

Acceptance:

- install smoke test passes in kind
- upgrade smoke test passes in kind
- uninstall smoke test passes in kind
- CRD retention or deletion policy is documented
- `kind get clusters` returns no remaining clusters after the gate

Planned verification target:

```sh
make verify-install-upgrade-uninstall-kind
```

## Release Gate Target

Goal:

- provide a single release gate entrypoint for `v0.2.0-beta.1`

Target command:

```sh
make verify-release-v0.2-beta
```

Expected sequence:

```text
verify-v0.2-alpha
verify-e2e-kind
verify-investigation-kind
verify-image-metadata
verify-reproducible-image
verify-helm-version
verify-no-latest
verify-install-upgrade-uninstall-kind
verify-no-kind-clusters
```

Acceptance:

- full release gate passes on a clean branch synchronized with `origin/main`
- full release gate uses the intended release image reference
- release notes, manifest version, chart version, image labels, and embedded binary revision all point to the same commit
- only after this gate passes should `v0.2.0-beta.1` be tagged
