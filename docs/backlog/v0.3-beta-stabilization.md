# v0.3 Beta Stabilization Backlog

This backlog tracks the schema-compatible stabilization work after the initial `v0.3` beta publications. The current published stabilization baseline is `v0.3.0-beta.3`.

The project has moved from foundation design into evidence-driven stabilization:

```text
P0 foundation:        COMPLETE
schema freeze:        PASSED
release gate:         PASSED
beta publication:     COMPLETE
provenance:           VERIFIED
```

The main question is no longer whether the RCA control-plane contract exists. The next question is whether real investigations are accurate, bounded, explainable, and useful enough for platform teams to trust.

## Active Phase

```text
v0.3 Beta Stabilization
and Evidence-Driven Optimization
```

`v0.3.x` should stay schema-compatible and focus on convergence:

- correctness bugs
- security issues
- provider adapter fixes
- verifier rule fixes
- replay fixture expansion
- installation and upgrade experience
- metrics, dashboard, and diagnostics
- real-cluster compatibility findings

Do not treat the following as normal `v0.3.x` bug fixes:

- new canonical schema fields
- changed frozen enum semantics
- changed execution or digest identity
- expanded remediation behavior
- unrestricted agent loops

If one of those changes is unavoidable, it must be tracked as a `v0.4` candidate or an explicit v0.3 schema-freeze exception.

## Product Baseline Metrics

Before optimizing prompts or provider behavior, establish a measurable RCA quality baseline.

| Area | Metrics |
| --- | --- |
| Root-cause quality | root-cause entity accuracy, root-cause type accuracy |
| Evidence quality | evidence precision, evidence recall |
| Model reliability | unsupported claim rate |
| Conservative behavior | abstention quality, unsafe `NoIssueFound` rate |
| Verifier behavior | `Supported`, `Inferred`, `Unsupported`, `Contradicted` distribution |
| Execution efficiency | investigation latency, checkpoint reuse |
| Datasource cost | query count, series count, sample count, log entry count |
| Model cost | input tokens, output tokens, provider request count |
| Stability | provider failures, retry count, degraded executions |
| Detection quality | false positives, false negatives |

Without this baseline, optimization can make answers sound better without proving that they are more accurate, cheaper, or more trustworthy.

## Dogfooding Scenarios

Collect real or replayable cases for these scenarios:

- Deployment rollout failure
- `ImagePullBackOff`
- `CrashLoopBackOff`
- `OOMKilled`
- readiness mismatch
- Service port mismatch
- dependency unavailable
- latency regression
- partial Prometheus or Loki outage
- contradictory evidence
- normal case with no issue

Each scenario should record:

```text
scenario
expected diagnosis
actual verdict
claims
verification statuses
missing evidence
query cost
latency
provider and token cost
human judgment
```

These records become the evaluation corpus for future provider, verifier, and evidence-selection work.

### Deterministic Baseline Checkpoint

The first offline corpus (`canonical-five-v1`) is executable with
`make verify-rca-quality-baseline` and covers Deployment rollout latency
regression, `ImagePullBackOff`, `CrashLoopBackOff`, `OOMKilled`, and a normal
latency case. It records expected and actual diagnosis, evidence
precision/recall, claim verification distribution, unsafe `NoIssueFound`,
datasource query count, provider request count, and terminal checkpoint reuse.

The 2026-08-11 baseline passed 5/5 with root-cause type/entity accuracy 1.00,
evidence precision/recall 1.00, unsafe `NoIssueFound` rate 0, checkpoint reuse
rate 1.00, 7 queries, and 4 fixture-provider requests. Unsupported claim rate
is 0.125 because the ImagePull provider summary is intentionally retained as
`Unsupported` while its evidence-linked cause is `Supported`. Token usage and
meaningful wall-clock latency are unavailable from deterministic fixture
providers and must not be reported as measured zero. Durable report:
[`artifacts/rca-quality-baseline-20260811-959fec2/report.md`](artifacts/rca-quality-baseline-20260811-959fec2/report.md).

The second corpus (`boundary-nine-v2`) adds readiness mismatch, dependency
unavailable, partial datasource failure, and contradictory evidence. It passed
9/9 with the earlier diagnosis/evidence metrics still at 1.00, failure-contract
accuracy 1.00, unsafe `NoIssueFound` 0, checkpoint reuse 1.00, 12 queries, and
7 fixture-provider requests. Verification distribution is 11 Supported, 1
Unsupported, and 2 Contradicted claims. Durable report:
[`artifacts/rca-quality-baseline-boundary-nine-20260811-4ab75da/report.md`](artifacts/rca-quality-baseline-boundary-nine-20260811-4ab75da/report.md).

This batch also fixed a verifier false contradiction: `not ready` is a negative
health state and must not be interpreted as the healthy marker `ready`.
Genuinely normal or below-threshold evidence continues to contradict incident
claims.

The third corpus (`operations-twelve-v3`) adds Service port mismatch and full
Prometheus/Loki outages. It passed 12/12 with diagnosis/evidence metrics and
failure-contract accuracy at 1.00, unsafe `NoIssueFound` 0, checkpoint reuse
1.00, 15 queries, and 8 fixture-provider requests. Durable report:
[`artifacts/rca-quality-baseline-operations-twelve-20260811-831103f/report.md`](artifacts/rca-quality-baseline-operations-twelve-20260811-831103f/report.md).

Provider usage parsing now covers OpenAI, Claude, and Gemini and flows through
reasoning into `status.execution`. Cluster validation measured a 3-second
successful provider path with 321 input / 87 output provider-reported tokens;
the paired OOM evidence-gated path made zero provider requests. Durable report:
[`artifacts/runtime-rca-efficiency-20260811-65a166d/report.md`](artifacts/runtime-rca-efficiency-20260811-65a166d/report.md).

## Optimization Order

Prioritize deterministic components before provider prompting:

```text
1. target resolution
2. evidence profiles
3. normalization
4. L3 verifier
5. NoIssueFound gates
6. provider reasoning
```

If evidence is incomplete or points at the wrong resource, provider output quality is not the first problem to solve.

## Experiment Tracks

Experimental work is allowed, but should remain behind feature flags, internal config, or replay-only paths until it has measurable value.

### Evidence Bundle Ablation

Compare RCA quality while progressively adding evidence:

```text
Kubernetes Events only
+ Deployment conditions
+ Prometheus
+ Loki
```

Measure which evidence improves diagnosis and which evidence only increases cost or noise.

### Verifier Ablation

Compare:

```text
no verifier
L1 schema verifier
L1 + L2 evidence verifier
L1 + L2 + L3 domain verifier
```

Track unsupported claim rate, contradicted claims, confidence bounding, and unsafe `NoIssueFound` outcomes.

### Context Compaction

Compare:

```text
full normalized observations
aggregated observations
high-relevance evidence only
```

Track token use, latency, evidence recall, and final RCA quality.

### Provider Comparison

Run the same evidence bundle through:

```text
heuristic
OpenAI
Claude
Gemini
```

Compare:

- root-cause entity
- root-cause type
- evidence citation quality
- unsupported claim count
- willingness to return `Inconclusive`
- verifier downgrade rate
- latency
- token usage
- cost

The expected outcome may be a routing strategy rather than one universal best provider:

```text
clear Kubernetes failure -> heuristic
complex cross-source case -> hosted provider
low evidence completeness -> abstain or avoid hosted provider
```

### Provider Fallback

Replay:

```text
hosted provider unavailable
malformed provider response
data policy rejected
token budget exceeded
```

Expected behavior:

- local fallback remains available
- policy rejection is auditable
- degraded or inconclusive RCA is preferred over unsupported confident output
- provider failures do not corrupt canonical status

### Query Plan Optimization

Compare:

```text
fixed full query set
profile-based query set
staged query set
bounded adaptive query set
```

Bounded adaptive investigation remains experimental and must not become the default v0.3 path.

## Backlog Categories

Use these labels for post-beta work:

```text
Beta blocker
Quality improvement
Efficiency
Experimental
```

`Beta blocker` includes correctness, security, data loss, invalid RCA status, and install or upgrade failure.

`Quality improvement` includes evidence profile refinement, verifier rules, provider adapter accuracy, and `NoIssueFound` precision.

`Efficiency` includes query count, latency, token usage, and evidence compaction.

`Experimental` includes adaptive investigation, new rule packs, additional provider modes, and broader workflow experiments.

Only blockers and low-risk quality improvements should enter the v0.3 stable path.

```text
schema changes:            NONE

RBAC least privilege:      default read-only RCA profile
legacy path isolation:     explicit opt-in
remediation isolation:     explicit controller and RBAC opt-in

```

`v0.3.0-beta.2` did not overwrite or move the published `v0.3.0-beta.1` tag or artifacts. Future fixes should publish a new immutable beta tag.

## Not Prioritized For v0.3.x

Do not prioritize these until the RCA quality baseline is established:

- distributed worker pool
- multi-cluster hub
- unrestricted agent loop
- broad remediation workflows
- approval UI
- large external provider matrix
- generic workflow engine

These features increase product breadth without necessarily improving the core trust question.

## Exit Toward Stable

Do not promote the beta by ticket count alone. Promotion should require evidence:

- core scenarios have stable replay results
- no high-risk schema or migration blocker remains
- `NoIssueFound` has no obvious dangerous false negatives
- unsupported claim rate is acceptable
- provider failure safely degrades
- install, upgrade, and uninstall remain stable
- real-cluster dogfooding has no major blocker

The key product question is:

```text
Can users trust the RCA result in a real incident, and can they tell when they should not trust it?
```
