# v0.3 Naming And API Review

This review records the current naming decision before the `v0.3` RCA contract moves toward schema freeze.

Product naming is tracked separately in
[v0.3 product rename](v0.3-product-rename.md). The product may move to the
`FluxSeer RCA` display name without changing the current v1alpha1 Kubernetes API
identity.

## Decision

Do not rename existing v1alpha1 CRDs in the current `v0.3` hardening cut.

The current API group and resource names remain:

```text
aiops.platform/v1alpha1
DataSource
ModelProvider
RiskRule
RiskSignal
InvestigationRequest
RemediationPlan
AgentAction
```

Rationale:

- `v0.2.0-beta.1` is already published with these names.
- GitOps overlays, Helm CRDs, examples, and release assets depend on these names.
- The current hardening work is about RCA trust semantics, not a breaking API migration.
- Renaming now would force migration mechanics before the status contract is stable.

## Reviewed Alternatives

### API Group

Candidate:

```text
fluxagent.io/v1alpha1
aiops.fluxseer.com/v1alpha1
```

Decision:

```text
Defer.
```

A future API group migration must include conversion or explicit migration guidance. It should not be mixed into the `v0.3` schema-freeze work.

### `ModelProvider`

Candidate:

```text
ReasoningProvider
RCAProvider
```

Decision:

```text
Keep ModelProvider for v1alpha1.
```

`ReasoningProvider` is semantically clearer for the long-term direction, but changing it now would break installed manifests. Provider-neutral RCA output and hosted-provider data policy already clarify that this resource controls reasoning providers, not arbitrary model usage.

### `AgentAction`

Candidate:

```text
ExecutionRequest
RemediationExecution
```

Decision:

```text
Keep AgentAction for v1alpha1, avoid expanding it in v0.3.
```

FluxAgent's current product boundary is read-only RCA. Remediation execution is not part of the `v0.3` foundation exit criteria. A future remediation-focused API can revisit this name when execution semantics are active.

### `InvestigationRequest.createRiskSignal`

Candidate:

```text
materializeRiskSignal
createFinding
publishRiskSignal
```

Decision:

```text
Keep createRiskSignal for v1alpha1.
```

The field is understandable and already used as a compatibility bridge. A future v1beta1 can choose a clearer materialization term if RiskSignal projection semantics change.

## Compatibility Rule

For the rest of `v0.3`:

- do not introduce breaking CRD renames
- keep compatibility fields as projections, not independent truth
- document any new field with migration semantics
- prefer additive fields over replacement fields
- move breaking naming changes to a future v1beta1 or v1 plan

## Follow-Up

Before a future breaking API cut:

1. Define the target API group.
2. Decide whether conversion webhooks are required.
3. Provide migration examples for Helm, Kustomize, and GitOps overlays.
4. Preserve old v1alpha1 semantics until the replacement path is documented and tested.
