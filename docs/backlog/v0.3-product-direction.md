# v0.3 Product Direction Backlog

This backlog tracks the work needed to sharpen FluxAgent's product direction after the `v0.3.0-beta.2` stabilization release.

Implementation status:

```text
All listed tickets have a first-pass implementation.
Runtime-integrated tickets are implemented in controller, gateway, Helm, or library code.
Experimental tickets remain disabled by default until a later runtime integration decision.
```

The product line should converge on:

```text
FluxAgent turns RCA into a governed, evidence-verifiable,
and replayable Kubernetes-native workflow.
```

FluxAgent should not compete primarily as the fastest alert-to-incident assistant. Alert assistants optimize the operator experience after an alert fires. FluxAgent should optimize the governance, policy boundary, verification, auditability, and replayability of RCA execution inside the Kubernetes API.

## Positioning

Recommended public distinction:

```text
KubeRCA:
Alert-to-incident workflow and operator-facing RCA assistant.

FluxAgent:
Kubernetes-native RCA control plane for defining,
governing, verifying, auditing, and replaying RCA workflows.
```

More concise:

```text
KubeRCA turns alerts into actionable incident context.

FluxAgent turns RCA into a governed, evidence-verifiable,
and replayable Kubernetes-native workflow.
```

Avoid overstating the current model as:

```text
make RCA evidence, reasoning, safety policy,
and execution state first-class Kubernetes resources
```

That wording can imply that evidence, reasoning, and policy are all independent Kubernetes resources. The stricter claim is:

```text
make RCA workflows, evidence-linked reasoning,
safety policy, and execution state first-class Kubernetes API state
```

or:

```text
FluxAgent makes RCA a governed, auditable,
and replayable Kubernetes-native workflow.
```

## Product Moats

### RCA Lifecycle Ownership

The authoritative execution record for canonical RCA is:

```text
InvestigationRequest.status
```

It should preserve:

- request identity
- attempt identity
- provider identity
- evidence references
- verdict
- claims
- verification status
- degradation
- query budget usage
- timestamps

### AI Authority Boundary

The controller and datasource adapters decide what may be collected. AI and heuristic providers reason only over the resulting bounded evidence bundle.

Required product boundary:

```text
AI has no Kubernetes credential.
AI has no direct datasource credential.
AI cannot generate arbitrary PromQL or LogQL.
AI cannot bypass redaction or egress policy.
AI cannot directly execute remediation.
```

This is a product choice:

```text
less agent autonomy
more platform governance
```

### Replay And Evaluation

Replay should become a core differentiator:

```text
recorded normalized evidence
+ provider configuration
+ RCA contract version
+ verifier version
-> replay
-> compare outputs
```

Replay enables:

- provider regression testing
- prompt and model upgrade comparison
- heuristic versus hosted AI comparison
- claim precision evaluation
- verifier regression testing
- rule-pack quality evaluation
- offline reruns without re-querying production datasources

## Milestones

### M0: Positioning And Contract Cleanup

Clarify the product promise without changing runtime behavior.

### M1: Canonical Runtime Convergence

Make all supported runtime paths converge on `InvestigationRequest.status` as the canonical RCA execution record.

### M2: Replay And Verification Moat

Add replay artifacts, evaluation harnesses, and evidence-linked solution assessment.

### M3: Controlled Proactive Value

Expand non-fatal anomaly value through explicit rule packs and profile templates, not unrestricted AI exploration.

### P0-4: `feat: make RiskRule CreateRequest the preferred RCA routing mode`

Goal:

Route recurring detections into the canonical `InvestigationRequest` workflow by default where practical.

Scope:

- make Helm rule packs prefer `RiskRule.spec.investigationPolicy.mode: CreateRequest`
- keep `DirectRiskSignal` as a compatibility path
- ensure deterministic request identity
- preserve lineage and finding identity
- keep optional `RiskSignal` projection

Acceptance:

- generated rule packs use `CreateRequest` by default
- repeated reconciles for the same incident update the same deterministic request
- `InvestigationRequest.status` owns canonical RCA output
- `RiskSignal` is a materialized or compatibility projection
- `DirectRiskSignal` is documented as deprecated compatibility behavior

Implemented status:

- built-in Helm rule packs render `investigationPolicy.mode: CreateRequest`
- built-in Helm rule packs set `createRiskSignal: true` to preserve optional materialized findings
- unset runtime mode remains `DirectRiskSignal` for v0.2 compatibility

### P0-5: `feat: apply provider data policy to RiskRule-triggered RCA paths`

Goal:

Prevent compatibility paths from bypassing hosted-provider data policy.

Scope:

- apply redaction, classification, egress policy, and audit to every hosted provider call
- cover direct `RiskRule` RCA while it still exists
- preserve heuristic fallback

Acceptance:

- no hosted provider call can bypass `ModelProvider.spec.dataPolicy`
- policy rejection prevents the hosted API request
- policy rejection is visible in bounded status or conditions
- heuristic fallback remains available when configured
- tests cover `RiskRule`-triggered provider data policy rejection

Implemented status:

- model gateway rejects hosted providers unless `spec.dataPolicy.allowExternalTransmission=true`
- direct `RiskRule` RCA now receives `ProviderDataPolicyDenied` before any hosted HTTP request
- provider fallback remains available for policy-denied hosted providers when configured
- canonical `InvestigationRequest` still owns the richer egress audit status surface

### P0-6: `feat: enforce InvestigationRequest evidence planning exclusivity`

Goal:

Make `spec.dataSources[]` and `spec.queries[]` mutually exclusive in runtime behavior and, if safe, CRD validation.

Scope:

- treat `dataSources[]` as controller-planned evidence
- treat `queries[]` as user-planned evidence
- fail ambiguous requests
- evaluate whether CEL validation can be added without schema-compatibility risk

Acceptance:

- requests that set both `dataSources[]` and `queries[]` surface `InvalidSpec`
- status or admission message explains the conflict
- docs describe the two ownership models
- tests cover both fields set, only `dataSources[]`, only `queries[]`, and neither set

Implemented status:

- runtime validation now rejects ambiguous requests that set both planning modes
- service preflight also returns `InvalidSpec` for ambiguous plans so non-controller callers cannot silently prefer `queries[]`
- CRD-level CEL admission validation remains a future optional hardening step

### P0-7: `feat: fail unsupported RawSnapshot retention explicitly`

Goal:

Make reserved evidence retention behavior explicit.

Scope:

- reject or fail `evidenceRetention.mode: RawSnapshot` at runtime

Acceptance:

- `RawSnapshot` produces `status.phase=Failed`
- condition includes `Ready=False`
- reason is `UnsupportedRetentionMode`

Implemented status:

- runtime validation rejects `RawSnapshot` before evidence collection

### P0-8: `chore: derive RBAC profile from feature flags`

Goal:

Explore adaptive evidence gathering while preserving the FluxAgent authority boundary.

Scope:

- disabled by default
- provider cannot directly query datasources
- adaptive query can only select allowlisted templates
- every step records deterministic execution metadata
- budget exhaustion produces `Inconclusive`

Acceptance:

- feature is opt-in and clearly experimental
- provider cannot bypass datasource policy

- query count budget limits the emitted steps
- no controller integration, provider tool loop, or autonomous datasource execution is enabled
