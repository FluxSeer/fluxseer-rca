# `v0.2` Adapter-neutral Backlog

This backlog turns the dependency-neutrality constraints into three implementation batches that can each land as a reviewable PR.

The sequencing goal is:

```text
first make datasource configuration explicit
then make datasource contracts capability-oriented
then make degraded behavior visible and reliable
```

## Batch 1: `DataSource` CRD

### Goal

Move datasource connection details out of environment-only wiring and toward a Kubernetes-native runtime contract.

### Scope

- add `DataSource` CRD under `aiops.platform/v1alpha1`
- support at least:
  - `prometheus`
  - `loki`
  - `kubernetesEvents`
- define spec fields for:
  - datasource `type`
  - `endpoint`
  - `timeout`
  - auth reference
  - TLS options when applicable
- add status fields for:
  - phase
  - observed generation
  - conditions
- update manager wiring so datasource registration can be built from `DataSource` resources, not only process env vars
- keep existing env-based demo path working during migration

### API Direction

Suggested shape:

```yaml
apiVersion: aiops.platform/v1alpha1
kind: DataSource
metadata:
  name: prometheus-main
  namespace: fluxagent-system
spec:
  type: prometheus
  endpoint: http://prometheus-server.monitoring.svc:9090
  timeout: 10s
  auth:
    type: none
```

### Expected Code Areas

- `api/v1alpha1/datasource_types.go`
- `config/crd/bases/aiops.platform_datasources.yaml`
- `config/samples/datasource-*.yaml`
- `internal/datasource/`
- `internal/operatorapp/run.go`
- `docs/crd-reference/datasource.md`

### Acceptance

1. a user can create `DataSource` objects for Prometheus, Loki, and Kubernetes Events
2. operator startup still works without external datasources
3. kind and local demo remain runnable without forcing real Prometheus or Loki install
4. at least one integration test proves registry construction from `DataSource` resources

### Not in This PR

- `RiskRule` `datasourceRef`
- capability-based datasource selection
- degraded condition propagation into `RiskRule` or `RiskSignal`

## Batch 2: Capability-based Datasource Contract

### Goal

Stop assuming that datasource choice is just one backend type string. Make rule evaluation depend on declared capabilities and normalized output.

### Scope

- extend datasource contract with declared capabilities
- enrich query and response normalization so evaluation logic can reason over:
  - metrics
  - logs
  - events
  - traces scaffolding
- introduce datasource factory or builder path that maps `DataSource.spec.type` to adapters cleanly
- start shifting `RiskRule` signal shape toward:
  - `datasourceRef`
  - `queryType`
  - `queryTemplate`
- keep backward compatibility with current inline `type` and `query` fields for one migration window if needed

### Contract Direction

Suggested interface target:

```go
type DataSource interface {
    Name() string
    Type() string
    Capabilities() Capabilities
    Query(ctx context.Context, req QueryRequest) (*QueryResult, error)
    HealthCheck(ctx context.Context) error
}
```

This batch should also move `QueryResult` closer to an evidence-oriented model instead of generic record bags only.

### Expected Code Areas

- `internal/datasource/interface.go`
- `internal/datasource/registry.go`
- `internal/datasource/*/adapter.go`
- `internal/rule/evaluator.go`
- `internal/rule/template.go`
- `api/v1alpha1/riskrule_types.go`
- `internal/controllers/riskrule_controller.go`

### Acceptance

1. adapters declare their capabilities explicitly
2. `RiskRule` evaluation can validate whether a referenced datasource supports the requested query type
3. Prometheus and Loki query handling remains template-driven
4. rule evaluation and reasoning consume normalized query output instead of backend-specific assumptions
5. migration path for existing demo rules is documented

### Not in This PR

- full degraded status fan-out across all resources
- executor or remediation changes
- broad multi-backend expansion beyond current adapters

## Batch 3: Degraded Status Conditions

### Goal

Make optional dependency failure visible, stable, and non-fatal.

### Scope

- standardize status conditions for:
  - `DataSource`
  - `RiskRule`
  - `RiskSignal` where relevant
- surface degraded cases such as:
  - datasource not found
  - unsupported adapter type
  - adapter health check failure
  - query capability mismatch
  - model provider missing or unavailable
- keep read-only signal creation working when partial evidence is still available
- ensure mutation-related flows remain fail-closed

### Condition Direction

Suggested condition families:

- `Ready`
- `Degraded`
- `Unsupported`
- `RCAReady`
- `DatasourceResolved`

Exact naming can change, but condition semantics should stay explicit and machine-readable.

### Expected Code Areas

- `api/v1alpha1/types.go`
- `internal/controllers/riskrule_controller.go`
- `internal/controllers/risksignal_controller.go`
- `internal/modelgateway/resolver.go`
- `internal/datasource/`
- `docs/crd-reference/risksignal.md`
- `docs/crd-reference/riskrule.md`
- `docs/crd-reference/datasource.md`

### Acceptance

1. missing optional integrations do not crash reconciliation
2. degraded states are visible through resource status conditions
3. `RiskSignal` can still be created when RCA enrichment fails but base evidence exists
4. tests cover partial-evidence success and clear degraded reporting
5. user-facing docs show how to inspect these conditions with `kubectl`

### Not in This PR

- approval workflow redesign
- executor semantics changes
- automatic remediation retries based on degraded conditions

## Recommended Order

1. merge `DataSource` CRD first because later batches need a stable config object
2. merge capability-oriented contract second because it reshapes adapter and rule evaluation internals
3. merge degraded conditions last because it depends on the new resource and contract surfaces already existing

## Cross-batch Guardrails

Every batch should preserve these constraints:

- `GOWORK=off go test ./...` stays green
- no PR may make Prometheus or Loki mandatory
- no PR may let provider output execute actions directly
- kind demo remains runnable
- read-only mode remains the default product truth
