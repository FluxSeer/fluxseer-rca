# v0.3 Runtime Error Matrix

This document records the current runtime validation matrix for `v0.3` RCA error/status reasons.

It intentionally separates cluster runtime evidence from unit, envtest, and mock-runtime coverage. A reason should not be called runtime-verified unless the artifact column points to an observed runtime output.

## Current Maturity Statement

```text
Direct RiskRule compatibility path:
  major safety boundaries have runtime regression evidence

Canonical InvestigationRequest:
  validation, target resolution, datasource resolution, query validation,
  provider resolution, provider egress policy, required-evidence gates,
  negative verdict generation, and loop prevention have runtime regression
  evidence

Provider execution, provider response validation, retention store, secret,
lifecycle, and extended datasource failure reasons:
  mostly have unit or integration coverage, but do not yet have a complete
  runtime evidence matrix
```

Runtime-tested:

- direct `RiskRule` finding and compatibility projection safety
- canonical validation, target resolution, datasource resolution, capability validation, query policy, query budget, provider resolution, provider egress policy, required-evidence gating, negative verdict generation, and loop prevention

Regression-covered but not fully runtime-tested:

- provider execution, provider response validation, fallback, verifier rejection, retention store, secret, lifecycle, and extended datasource failure reasons

## Runtime Audit Follow-Ups

The `bf35d5e` runtime contract matrix produced a 10/10 PASS result and fixed the dangerous `NoIssueFound` contamination case. The remaining gaps are audit-surface gaps, not failures of the covered runtime behavior:

- `ProviderDataPolicyDenied` and `ProviderDataPolicyRejected` currently prove rejection through controller status and egress audit attempts. The next safety-hardening test should add an independent mock provider access log or request counter and assert `providerRequestCount=0`.
- `NoIssueFound` currently proves the runtime outcome and the separation from contamination. The public status/report should eventually expose profile coverage, completed checks, incomplete checks, and issue match count so an external reviewer can distinguish "queried and clean" from "no evidence returned".
- Runtime reports should print fixed condition-contract checks explicitly, including complete condition set coverage and `observedGeneration` equality for terminal status conditions.

## Matrix Contract

Every runtime error-matrix row should preserve these fields:

| Column | Meaning |
| --- | --- |
| `reason` | Stable condition, failure, degradation, or blocking reason. |
| `stage` | Workflow stage: `Validation`, `TargetResolution`, `DataSourceResolution`, `QueryValidation`, `EvidenceCollection`, `ProviderResolution`, `ProviderEgressPolicy`, `Reasoning`, `Verification`, `Projection`, or `Persistence`. |
| `trigger` | Minimal input or dependency behavior that should produce the reason. |
| `testTier` | `unit`, `envtest`, `mock-runtime`, or `cluster`. |
| `runtimeFeasibility` | `direct`, `mock`, `special infra`, or `unit-only`. |
| `expectedPhase` | Expected `InvestigationRequest.status.phase`, when applicable. |
| `expectedOutcome` | Expected `InvestigationRequest.status.outcome`, when applicable. |
| `expectedConditions` | Required condition type/status/reason assertions. |
| `negativeAssertions` | Side effects that must not happen. |
| `runtimeIdentityRequired` | Whether the assertion requires runtime UID, generation, execution, provider, or linked-object identity. |
| `reachability` | Whether the reason is reachable through the public CRD/controller path, service-only, adapter-only, or admission/preflight only. |
| `status` | `NotStarted`, `Covered`, or `PASS`. |
| `artifact` | Runtime report path, test name, or other durable evidence. |

Status values:

| Status | Definition |
| --- | --- |
| `PASS` | Runtime artifact exists and matches expected positive and negative assertions. |
| `Covered` | Unit, envtest, or integration coverage exists, but no complete runtime artifact is recorded. |
| `NotStarted` | No dedicated matrix evidence has been recorded. |

## Negative Assertion Contract

Every cluster or mock-runtime scenario should explicitly assert the relevant counters and object side effects:

- `providerAttemptCount`
- `providerRequestCount`
- `egressAttemptCount`
- `datasourceQueryCount`
- `evidenceCount`
- `riskSignalCount`
- `remediationPlanCount`
- `agentActionCount`
- `executionPresent`
- `providerResultPresent`
- `linkedRiskSignalRef`

For preflight failures, the default negative assertion is:

```text
no evidence collection
no datasource query
no provider execution
no verified RCA
no remediation
no AgentAction
no RiskSignal projection unless the scenario explicitly tests projection
```

## Recommended Runtime Order

1. `ProviderDataPolicyDenied` / `ProviderDataPolicyRejected` with independent mock provider `providerRequestCount=0`
2. `NoIssueFound` with explicit coverage audit fields or report assertions
3. fixed terminal condition-set and `observedGeneration` report assertions
4. `ProviderUnavailable`
5. `ProviderRequestFailed`
6. `InvalidProviderResponse`
7. provider fallback success
8. `ProviderFallbackLoop`
9. `NoSupportedRootCauseClaims`
10. `RCAUnverified`
11. canonical OOMKilled event-only
12. canonical ImagePullBackOff structured evidence
13. `EvidenceRetentionWriteFailed`
14. `EvidenceRetentionStoreUnavailable`
15. TTL cleanup
