# FluxAgent `v0.2` Read-only RCA Plan

`v0.2` should move FluxAgent from a runnable `v0.1` demo and read-only `RiskSignal` operator to a configurable read-only RCA platform that other users can install, configure, and validate.

The main product truth remains unchanged:

- read-only by default
- Kubernetes-native control plane
- provider-neutral reasoning
- no production mutation in the default success path

## Product Goal

`v0.2` is:

```text
Configurable Read-only RCA Assistant
```

The goal is not autonomous repair. The goal is to let users define detection rules, collect evidence from supported datasources, produce a `RiskSignal`, and attach an RCA summary that remains operationally safe.

## Scope

The `v0.2` success path should support:

1. users define detection rules through CRDs
2. FluxAgent queries Kubernetes Events, Prometheus, and Loki
3. FluxAgent builds an evidence bundle
4. FluxAgent redacts sensitive evidence before provider-bound reasoning
5. FluxAgent generates a structured RCA summary
6. FluxAgent creates or updates a `RiskSignal`
7. FluxAgent sends notification output with the RCA summary

The `v0.2` success path should not:

1. execute remediation
2. create `AgentAction` by default
3. mutate production workloads
4. require external model credentials for a basic demo

## Dependency-neutrality Constraints

`v0.2` should improve configurability without re-introducing hard stack coupling.

Required constraints:

1. Prometheus and Loki stay optional datasource adapters.
2. the heuristic provider remains a first-class fallback path.
3. core reasoning and evidence handling stay expressed through FluxAgent domain types.
4. query intent stays reviewable and template-driven.
5. missing optional integrations degrade status, not process stability.

## Why Not Start With Executors

Broad executor work is the wrong next dependency because it forces the project into higher-risk concerns too early:

- RBAC boundaries
- approval lifecycle
- dry-run guarantees
- rollback semantics
- audit persistence
- dangerous action allowlists
- GitOps backend complexity

Those concerns matter, but they should follow a stronger read-only product. A better sequence is:

```text
v0.1: read-only RiskSignal demo
v0.2: configurable read-only RCA
v0.3: RemediationPlan draft only
v0.4: guardrails and approval
v0.5: safe executor
```

## New API Contracts

### `RiskRule`

`RiskRule` becomes the primary read-only detection input.

Responsibilities:

- target selectors
- datasource query definitions
- thresholds
- time windows
- severity
- notification settings
- AI RCA enablement

Example shape:

```yaml
apiVersion: aiops.platform/v1alpha1
kind: RiskRule
metadata:
  name: open-api-latency-regression
  namespace: fluxagent-system
spec:
  targetSelector:
    namespaceSelector:
      matchNames:
        - prod
    workloadSelector:
      matchLabels:
        app: open-api
  window: 10m
  severity: warning
  signals:
    - name: p95-latency
      datasourceRef:
        name: prometheus-main
      queryType: metric
      queryTemplate: |
        histogram_quantile(
          0.95,
          rate(http_request_duration_seconds_bucket{
            namespace="{{ .namespace }}",
            app="{{ .app }}"
          }[5m])
        )
      threshold:
        operator: ">"
        value: 1.5
    - name: error-logs
      datasourceRef:
        name: loki-main
      queryType: log
      queryTemplate: |
        {namespace="{{ .namespace }}", app="{{ .app }}"} |= "error"
      threshold:
        operator: "count_gt"
        value: 5
    - name: unhealthy-events
      datasourceRef:
        name: kubernetes-events
      queryType: event
      reasons:
        - Unhealthy
        - BackOff
        - Failed
        - OOMKilled
  notification:
    webhookRef:
      name: fluxagent-webhook
      key: url
  ai:
    rcaEnabled: true
    providerRef:
      name: default-model-provider
```

The key shift is that detection intent should live in a Kubernetes-native config resource instead of being expressed only through workload annotations.

The current first implementation batch is intentionally smaller than this end state. Today the schema still keeps inline signal `type` and query fields so the read-only RCA path can ship first. A follow-up batch can move connection details into a dedicated `DataSource` resource and let `RiskRule` depend on `datasourceRef` only.

### `ModelProvider`

`ModelProvider` becomes the runtime configuration contract for reasoning backends.

Responsibilities:

- provider selection
- model and endpoint settings
- auth via `SecretRef`
- timeouts and limits
- fallback to heuristic mode

Example shape:

```yaml
apiVersion: aiops.platform/v1alpha1
kind: ModelProvider
metadata:
  name: default-model-provider
  namespace: fluxagent-system
spec:
  provider: openai
  model: gpt-5.1
  apiKeySecretRef:
    name: openai-secret
    key: api-key
  timeout: 30s
  maxTokens: 2000
  fallbackProviderRef:
    name: heuristic-provider
```

The heuristic provider should remain a first-class path so the project stays runnable without external secrets.

## Internal Evidence Model

`v0.2` should not introduce an `EvidenceBundle` CRD yet.

Instead, use an internal model so the project can:

- avoid large raw payloads in etcd
- avoid leaking logs or secrets into CRD status
- keep the API surface smaller while the data model is still changing

Suggested starting point:

```go
type EvidenceBundle struct {
    Target     ResourceRef
    Window     TimeWindow
    Signals    []SignalEvidence
    Events     []EventEvidence
    Metrics    []MetricEvidence
    Logs       []LogEvidence
    Deployment DeploymentContext
    Summary    string
}
```

`RiskSignal` should remain the output resource, not the full evidence store. Persist summaries and references instead of raw large evidence bodies.

## `RiskSignal` Output Guidance

`RiskSignal` should stay narrow:

- phase and observed timestamps
- short human-readable summary
- structured RCA summary
- evidence references

It should not become the place where rule definitions, full logs, notification payloads, and provider prompts all accumulate.

## Model Gateway Direction

The current provider-neutral model abstraction should become a more explicit model gateway.

Suggested contract:

```go
type ModelProvider interface {
    Name() string
    Generate(ctx context.Context, req ModelRequest) (*ModelResponse, error)
    HealthCheck(ctx context.Context) error
}
```

Request shape:

```go
type ModelRequest struct {
    TaskType     string
    Incident     IncidentContext
    Evidence     EvidenceBundle
    OutputSchema OutputSchema
    Tools        []ToolSchema
}
```

Important `v0.2` rule: the model gateway may generate RCA and recommended actions, but it must not call execution tools.

The model is allowed to say:

```text
Check the recent rollout and inspect pod logs.
```

It is not allowed to execute:

```text
rollout pause
scale deployment
patch workload
```

## Structured RCA Output

Provider output should be validated structured JSON, not free-form text.

Example:

```json
{
  "summary": "open-api shows increased p95 latency after a recent rollout.",
  "severity": "warning",
  "confidence": 0.82,
  "suspectedCauses": [
    {
      "cause": "recent deployment regression",
      "confidence": 0.76,
      "evidenceRefs": ["prometheus:p95-latency", "loki:error-logs"]
    }
  ],
  "recommendedActions": [
    {
      "type": "diagnostics.collectPodLogs",
      "description": "Collect pod logs from open-api pods in the last 10 minutes.",
      "risk": "low",
      "execution": "manual"
    }
  ]
}
```

In `v0.2`, `recommendedActions` are advisory output only. They do not become `AgentAction`.

## Controller Shape

`RiskRuleReconciler` becomes the primary `v0.2` control loop.

Responsibilities:

1. watch `RiskRule`
2. discover matching workloads from selectors
3. query enabled datasources
4. build an `EvidenceBundle`
5. redact evidence before reasoning
6. invoke the reasoning engine or model gateway
7. create or update `RiskSignal`

Pseudo flow:

```go
func (r *RiskRuleReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
    rule := getRiskRule(req)
    targets := discoverTargets(rule.Spec.TargetSelector)

    for _, target := range targets {
        evidence := evidenceBuilder.Build(ctx, rule, target)
        if !evidence.HasRisk() {
            continue
        }

        redacted := redactor.RedactBundle(ctx, evidence)
        reasoningOutput := reasoningEngine.Analyze(ctx, redacted)
        riskSignal := buildRiskSignal(rule, target, evidence, reasoningOutput)
        upsertRiskSignal(riskSignal)
    }

    return ctrl.Result{RequeueAfter: rule.Spec.Interval}, nil
}
```

## Safety Requirements

`v0.2` must keep these guarantees:

1. read-only by default
2. `RiskRule` may query datasources but may not declare executable remediation
3. `ModelProvider` may generate RCA and advice but may not execute actions
4. `RiskSignal` describes risk and evidence references only
5. `RemediationPlan` and `AgentAction` stay disabled in the default `v0.2` flow
6. all provider credentials are referenced through Kubernetes secrets
7. evidence is redacted before provider submission

## Evidence Redaction

Evidence redaction is not optional once external providers are involved.

Start with basic masking for:

- bearer tokens
- passwords
- API keys
- authorization headers
- connection-string passwords
- Kubernetes secret values
- optionally email addresses

Suggested package:

```text
internal/evidence/redactor.go
```

Suggested contract:

```go
type Redactor interface {
    Redact(ctx context.Context, input string) string
}
```

## Test Priorities

`v0.2` should add:

- `RiskRuleReconciler` tests
- selector matching tests
- Prometheus query template tests
- Loki query template tests
- `EvidenceBundle` builder tests
- evidence redaction tests
- model-gateway routing tests
- structured output validation tests
- `RiskSignal` upsert idempotency tests

Two tests are mandatory for the product promise:

1. idempotency
2. no mutation when remediation is disabled

Idempotency means the same rule, target, and window should update the same `RiskSignal` instead of creating garbage resources repeatedly.

No mutation means that when remediation is disabled, the system must not create `RemediationPlan` or `AgentAction`.

## Demo Direction

The kind demo should evolve toward:

```bash
make demo-up
make apply-riskrule
make inject-fault
kubectl get riskrule -A
kubectl get risksignal -A
kubectl describe risksignal ...
make demo-status
make demo-down
```

Suggested examples:

```text
examples/riskrules/
├─ latency-regression.yaml
├─ crashloop-events.yaml
├─ error-logs.yaml
```

This makes the project look like a configurable operator instead of a hard-coded demo.

## Definition of Done

`v0.2` is done when:

1. `RiskRule` CRD exists
2. `ModelProvider` CRD exists
3. `RiskRuleReconciler` discovers workloads through selectors
4. Kubernetes Events, Prometheus, and Loki query templates work
5. an internal `EvidenceBundle` exists
6. evidence redaction is enforced before provider calls
7. heuristic mode is a first-class provider path
8. at least one non-heuristic provider or local endpoint works
9. structured RCA summaries are persisted into `RiskSignal`
10. notifications include RCA summary content
11. the kind demo is `RiskRule`-driven
12. `go test ./...` stays green
13. remediation-disabled mode does not create `RemediationPlan` or `AgentAction`
14. optional datasource and model-provider failures surface through degraded status instead of crashing the operator
