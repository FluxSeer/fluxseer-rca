# v0.3 Architecture Hardening Backlog

This backlog captures follow-up work from the `v0.3.0-beta.2` architecture review.

The current architecture direction is sound:

```text
FluxAgent governs how RCA evidence is collected,
how AI is allowed to reason,
how claims are verified,
and how execution state is recorded in Kubernetes.
```

The remaining work is not a positioning reset. It is contract hardening so every runtime path, external integration, evidence store, and remediation flow can be safely consumed as Kubernetes API state.

## P0: Canonical Runtime Contract

### P0-1: `feat: make RiskRule canonical investigation routing the runtime default`

Goal:

Make recurring detections route to the canonical `InvestigationRequest` workflow by default.

Scope:

- default new Helm-rendered rules to `investigationPolicy.mode: CreateRequest`
- keep `DirectRiskSignal` only as an explicit compatibility path
- document `DirectRiskSignalCompatibility` as non-canonical
- preserve deterministic request identity and optional `RiskSignal` projection

Acceptance:

- default rule packs render `CreateRequest`
- direct `RiskSignal` RCA is opt-in and clearly labeled compatibility
- canonical `InvestigationRequest.status` remains the only authoritative RCA execution record
- migration docs explain how existing direct rules continue to work

Status:

- built-in rule packs already render `CreateRequest`
- runtime default for an unset mode remains `DirectRiskSignal` for compatibility
- remaining work is a compatibility and migration decision

### P0-2: `feat: re-evaluate data egress policy for fallback providers`

Goal:

Prevent fallback providers from inheriting the primary provider's egress decision.

Scope:

- resolve fallback provider independently
- filter evidence against fallback provider policy
- re-evaluate `allowExternalTransmission`
- re-evaluate classification, denied sensitivity tags, evidence kinds, and redaction requirements
- persist a distinct fallback attempt audit

Acceptance:

- hosted fallback providers are never called without their own policy approval
- local heuristic fallback does not require external egress opt-in
- each provider attempt records a bounded egress/audit decision
- tests cover hosted-to-hosted, hosted-to-local, and local-to-hosted fallback cases

### P0-3: `feat: formalize InvestigationRequest conditions contract`

Goal:

Make canonical RCA status easier for other Kubernetes tools to consume.

Candidate condition types:

```text
Accepted
TargetResolved
EvidenceReady
RCAReady
Verified
Degraded
EgressAllowed
ReplayReady
RemediationReady
```

Scope:

- define stable condition types and reason enums
- document legal status combinations
- ensure conditions include `observedGeneration`
- avoid requiring consumers to parse deep provider execution fields for common health checks

Acceptance:

- Argo CD, Argo Events, policy engines, and dashboards can consume top-level conditions
- reasons are machine-readable and stable
- condition contract is documented separately from provider-specific status details

### P0-4: `feat: harden AgentAction approval authority`

Goal:

Stop treating `spec.approvedBy` as the sole execution authorization boundary.

Scope:

- design a non-forgeable approval record or controller-owned approval status
- bind approval to request UID, plan/action digest, generation, approver identity, and timestamp
- prevent ordinary action editors from self-approving by writing a string
- preserve current experimental `AgentAction` compatibility until migration is defined

Acceptance:

- executor checks an approval record that cannot be forged by editing `AgentAction.spec.approvedBy`
- approval is tied to a specific action generation and digest
- existing experimental remediation remains disabled by default
- migration behavior is documented

### P0-5: `feat: move dry-run result semantics out of desired spec`

Goal:

Separate desired remediation action from controller-observed dry-run outcome.

Scope:

- keep user intent in `spec`
- move or project dry-run observations into `status`
- preserve compatibility with current `spec.dryRunResult` during migration

Acceptance:

- dry-run outcome is controller-owned status
- spec remains user-desired state
- compatibility projection is documented if the old field remains

### P0-6: `feat: add post-action remediation effectiveness verification`

Goal:

Distinguish successful execution from successful remediation.

Scope:

- track execution result separately from effectiveness result
- support post-action verification by rollout check, signal re-query, or follow-up `InvestigationRequest`
- record ineffective remediation without claiming executor failure

Acceptance:

- `ExecutionSucceeded=True` does not imply `RemediationEffective=True`
- failed effectiveness verification can link to evidence or an investigation request
- remediation remains disabled by default

## P1: Evidence And Projection Hardening

### P1-1: `docs: mark local-filesystem snapshot store development-only`

Goal:

Avoid presenting local evidence snapshots as durable production storage.

Acceptance:

- docs state local filesystem snapshots are not encrypted
- docs state snapshots do not have automatic garbage collection in beta
- docs recommend object storage, encryption, and retention controller work for production

### P1-2: `feat: add durable evidence storage backends`

Candidate backends:

```text
S3
GCS
Azure Blob
S3-compatible object storage
PVC-backed store
```

Acceptance:

- payload refs do not expose paths or credentials
- encryption state is recorded
- retention and garbage collection behavior is explicit

### P1-3: `feat: add query retention policy`

Goal:

Reduce leakage risk from persisted rendered queries.

Candidate policy:

```yaml
queryRetention:
  mode: DigestOnly | Redacted | Full
```

Default:

```text
DigestOnly
```

Acceptance:

- `EvidenceRef` can avoid storing full rendered query text
- query digest remains available for replay/audit identity
- redacted query storage is explicit and policy-controlled

### P1-4: `feat: make RiskSignal a compact RCA projection`

Goal:

Reduce duplicated RCA state and divergence risk.

Scope:

- prefer `investigationRef`
- keep finding identity, severity, phase, and compact summary
- keep selected evidence refs only when necessary
- avoid duplicating full RCA claims and evidence bundles

Acceptance:

- `RiskSignal` cannot become a second source of truth for RCA execution
- projection behavior is deterministic
- compatibility RCA fields are documented as projections or legacy fields

### P1-5: `feat: persist verifier and collector versions`

Goal:

Make replay and idempotency easier to interpret after verifier or collector changes.

Scope:

- store `verifierVersion`
- store `verificationPolicyVersion`
- consider `collectorVersion` and datasource adapter version metadata

Acceptance:

- reused provider results can be distinguished from newly evaluated verifier outcomes
- replay fixtures can explain observation normalization differences

## P2: Ecosystem Integration Contract

### P2-1: `docs: add Kubernetes ecosystem integration contract`

Goal:

Document how external controllers and tools should consume FluxAgent state.

Scope:

- labels and annotations
- conditions and reason enums
- kube-state-metrics mapping
- Prometheus recording rules
- Argo CD / Argo Events consumption patterns
- Kyverno policy examples

Acceptance:

- external tools can consume top-level conditions before parsing deep status fields
- examples do not require provider-specific fields
- runtime architecture and release pipeline details remain separate

### P2-2: `docs: add Alertmanager and external alert producer examples`

Goal:

Clarify future alert-adapter boundaries without making FluxAgent an alert assistant.

Acceptance:

- examples create `InvestigationRequest` or `RiskRule` inputs
- FluxAgent remains the RCA control plane
- external producer identity and lineage are preserved
