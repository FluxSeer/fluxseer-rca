# FluxAgent `v0.3` Alpha Plan

`v0.3` should not try to outgrow into a general-purpose agent platform first.

The next product layer should be:

```text
Operator-first Investigation Experience
```

In practical terms:

- keep `RiskRule`-driven background detection
- keep read-only as the default safety boundary
- add an ad-hoc investigation entrypoint
- let users trigger RCA for a workload on demand
- keep investigation results auditable and replayable
- avoid jumping straight into remediation or direct tool execution

## Product Position

The intended distinction is:

```text
HolmesGPT: agent-first investigation platform
FluxAgent: CRD-first AI SRE control plane with read-only investigation workflows
```

That distinction matters because FluxAgent already has an advantage in:

- Kubernetes-native workflow state
- CRD status and conditions
- explicit safety boundaries
- declarative configuration and auditability

The missing layer is not another executor. The missing layer is a direct investigation entrypoint.

## Why `InvestigationRequest`

Current `v0.2` alpha candidate capabilities are strong on background detection:

- `RiskRule`
- `DataSource`
- `ModelProvider`
- `RiskSignal`
- degraded conditions
- read-only RCA generation

What is still missing is the user intent:

```text
Investigate this workload now and tell me what is going on.
```

That should become a first-class Kubernetes resource instead of being hidden inside a future chat UI.

## Goal

`v0.3` alpha should introduce:

```text
InvestigationRequest + read-only investigation workflow
```

The first alpha goal is not an interactive assistant. The first alpha goal is a stable operator-native contract that other entrypoints can call.

Future entrypoints may include:

- CLI
- thin UI
- webhook bridge
- chat bridge

They should all compile down to the same CRD workflow.

## New CRD: `InvestigationRequest`

`InvestigationRequest` represents one human-triggered or system-triggered read-only investigation.

It should answer:

```text
For this target, in this time range, collect evidence from these datasources and produce RCA.
```

It should not mean:

- a standing risk policy
- a background scheduler
- an execution request
- an approved remediation action

### Spec Shape

Suggested first shape:

```yaml
apiVersion: aiops.platform/v1alpha1
kind: InvestigationRequest
metadata:
  name: investigate-open-api
  namespace: fluxagent-system
spec:
  target:
    kind: Deployment
    namespace: prod
    name: open-api
    apiVersion: apps/v1

  timeRange:
    lookback: 15m

  question: |
    Why did open-api latency increase after the latest rollout?

  dataSources:
    - name: kubernetes-events
    - name: prometheus-main
    - name: loki-main

  modelProviderRef:
    name: heuristic-provider

  mode: readOnly
  createRiskSignal: false
```

### Status Shape

Suggested first status:

```yaml
status:
  phase: Completed
  observedGeneration: 1
  startedAt: "2026-07-05T10:00:00Z"
  completedAt: "2026-07-05T10:01:20Z"

  summary: "open-api shows elevated latency after the latest rollout."
  hypothesis: "Likely rollout regression combined with application error spikes."
  confidence: 0.78
  provider: heuristic-provider

  evidenceRefs:
    - type: metric
      datasource: prometheus-main
      summary: "p95 latency crossed threshold in the last 15 minutes"
    - type: log
      datasource: loki-main
      summary: "error logs increased after deployment restart"
    - type: event
      datasource: kubernetes-events
      summary: "Unhealthy and BackOff events detected on target pods"

  linkedRiskSignalRef:
    name: open-api-investigation-risk
    namespace: prod

  conditions:
    - type: Ready
      status: "True"
      reason: InvestigationCompleted
    - type: EvidenceCollectionReady
      status: "True"
      reason: AllDataSourcesReady
    - type: RCAReady
      status: "True"
      reason: ProviderSucceeded
```

## Lifecycle

Expected lifecycle:

1. request created
2. target resolved
3. datasource references validated
4. evidence collected
5. evidence redacted
6. RCA generated
7. status persisted
8. optional `RiskSignal` created

Suggested phases:

- `Pending`
- `CollectingEvidence`
- `GeneratingRCA`
- `Completed`
- `Failed`
- `Degraded`

Suggested condition types:

- `Ready`
- `TargetResolved`
- `EvidenceCollectionReady`
- `RCAReady`
- `Degraded`

Typical degraded reasons should mirror existing style:

- `DataSourceNotFound`
- `CapabilityMismatch`
- `ProviderNotFound`
- `ProviderUnavailable`
- `InvalidProviderResponse`

## Architecture Adjustment

The next architecture should be described as three paths, not two:

```text
1. Background detection path
2. Ad-hoc investigation path
3. Optional guarded remediation path
```

### 1. Background Detection Path

This remains:

```text
RiskRule
  -> RiskRuleReconciler
  -> datasource query
  -> Evidence
  -> ModelGateway
  -> RiskSignal
  -> Notification
```

### 2. Ad-hoc Investigation Path

This is the new path:

```text
InvestigationRequest
  -> InvestigationRequestReconciler
  -> target resolution
  -> datasource query
  -> Evidence bundle
  -> Evidence redaction
  -> ModelGateway
  -> InvestigationRequest.status
  -> optional RiskSignal
```

### 3. Optional Guarded Remediation Path

This stays separate and opt-in:

```text
RiskSignal
  -> RemediationPlan
  -> Guardrails
  -> AgentAction
  -> Executor
```

## New Internal Layer

`v0.3` should add an explicit investigation service layer between controllers and adapters.

Suggested responsibility split:

- `InvestigationRequestReconciler`
  - reconcile CRD lifecycle
  - own status transitions
  - own optional `RiskSignal` creation
- `investigation.Service`
  - resolve targets
  - orchestrate datasource queries
  - normalize evidence
  - call redaction and model gateway
- `modelgateway.Gateway`
  - stay provider-neutral
  - stay execution-blind

This keeps investigation logic reusable between:

- `RiskRule`
- `InvestigationRequest`
- future CLI or UI wrappers

## Relationship With Existing CRDs

### `RiskRule`

`RiskRule` remains the background policy contract.

It answers:

```text
What should FluxAgent keep checking automatically?
```

### `InvestigationRequest`

`InvestigationRequest` becomes the ad-hoc investigation contract.

It answers:

```text
What should FluxAgent investigate now?
```

### `RiskSignal`

`RiskSignal` remains the detected-risk record and cross-workflow handoff object.

It answers:

```text
What risk did FluxAgent observe and preserve as workflow state?
```

An `InvestigationRequest` should not be forced to create a `RiskSignal`, but it should be able to opt in.

## UX Direction

The UX sequence should be:

1. CRD first
2. thin CLI second
3. thin UI third

Do not reverse that order.

If a CLI is added, it should be a wrapper around CRD creation:

```bash
fluxagent investigate deployment open-api \
  -n prod \
  --lookback 15m \
  --question "Why did latency increase after rollout?"
```

That command should create an `InvestigationRequest` and watch status. It should not introduce a separate control plane.

## Non-goals For The First Alpha

Do not make the first `v0.3` batch responsible for:

- chat memory
- long-running conversations
- arbitrary tool calling
- direct executor access from the investigation path
- autonomous remediation
- multi-cluster federation
- large Web UI work

Those are later expansion topics. They should not define the first implementation slice.

## First Implementation Batch

Recommended first batch:

1. add `InvestigationRequest` CRD and status conditions
2. add `InvestigationRequestReconciler` skeleton
3. introduce reusable `investigation.Service`
4. reuse existing datasource, redaction, and model gateway layers
5. persist RCA into `InvestigationRequest.status`
6. keep `createRiskSignal` disabled by default

This batch is enough to establish the new product layer without overcommitting to UI or remediation semantics.
