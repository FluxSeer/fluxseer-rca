# v0.3 Trustworthy RCA Contract

`v0.3` should focus on trustworthy RCA, not product breadth.

Goal:

```text
InvestigationRequest
-> bounded evidence collection
-> structured hypotheses
-> evidence-linked claims
-> independent verification
-> auditable RCA status
```

## P0: Structured RCA Schema

Add a first-class RCA status contract for `InvestigationRequest`.

Required fields:

- verdict summary
- verdict outcome
- root cause entity
- root cause type
- confidence
- claims
- evidence references
- alternative hypotheses
- missing evidence
- degradation metadata
- provider execution metadata

Acceptance:

- important conclusions are represented as claims
- every claim has a verification status
- unsupported or inferred claims are not marked as supported
- existing simple `summary` and `hypothesis` fields remain backward-compatible during transition
- confidence is documented as a ranking score, not a calibrated probability
- abstention outcomes such as `Inconclusive` are representable without failing the workflow

## P0: Evidence Provenance

Each compact evidence reference should record:

- datasource
- capability
- query digest
- time range
- collected timestamp
- content digest
- redaction profile
- truncation flag
- original size
- retention policy

Acceptance:

- raw payload persistence remains optional and disabled by default
- evidence metadata is sufficient for audit and replay planning
- redaction and truncation are visible to RCA consumers

## P0: Normalized Observation Contract

Add a normalized observation shape before provider-bound reasoning.

Initial observation examples:

- request rate increased by ratio against baseline
- error rate crossed threshold
- p95 latency increased by ratio against baseline
- CPU throttling increased
- memory usage approached limit
- timeout, retry, rate-limit, or connection pool log patterns matched
- Kubernetes unhealthy events matched

Acceptance:

- hosted providers receive normalized observations instead of raw datasource payloads by default
- observation IDs can be referenced by RCA claims
- query digests and content digests are recorded for audit
- redaction profile and truncation state are visible
- heuristic and hosted providers consume the same incident fixture shape

## P0: Provider-neutral RCA Output

Do not create provider-specific RCA contracts.

All providers should normalize into the same structured RCA shape:

- verdict outcome
- verdict summary
- confidence level, score, and method
- evidence-linked claims
- missing evidence
- alternative hypotheses
- degradation metadata
- provider execution metadata

Expected provider differences:

| Provider | Expected behavior |
| --- | --- |
| heuristic | Summarize explicit matching signals and avoid unsupported causal inference. |
| OpenAI, Claude, Gemini | Correlate timing, cross-source evidence, and alternative hypotheses inside bounded context. |
| verifier | Validate whether claims are supported by the collected evidence. |

Acceptance:

- provider adapters cannot expose incompatible status schemas
- `InvestigationRequest.status` is the canonical RCA result
- `RiskSignal` stores only materialized risk summary, lineage, and compact evidence references
- unsupported provider claims are marked as `Unsupported`, `Inferred`, or `Unverified`

## P0: Signal Lineage And Loop Prevention

Discovered `RiskSignal` emission must not create investigation loops.

Target status and annotations:

```yaml
status:
  lineage:
    sourceSignalRef:
      namespace: prod
      name: checkout-latency
    investigationDepth: 1
---
metadata:
  annotations:
    fluxagent.io/discovered-by-investigation: investigate-checkout
```

Default policy:

- a `RiskSignal` discovered by an `InvestigationRequest` does not automatically trigger another `InvestigationRequest`
- reinvestigation of discovered signals requires an explicit policy opt-in
- maximum investigation depth is enforced

Required deduplication inputs:

- source lineage
- finding fingerprint
- target reference
- observed generation
- event or evidence window
- cooldown window

Acceptance:

- `RiskSignal -> InvestigationRequest -> discovered RiskSignal` cannot recurse by default
- emitted discovered signals are traceable to the investigation that created them
- duplicate findings update or reference an existing signal instead of creating unbounded objects

## P0: Claim Verifier

Add a verification pass after RCA generation.

First implementation can be heuristic.

It should verify:

- each claim has evidence references
- evidence type is relevant to the claim
- contradictory evidence is surfaced
- confidence does not exceed evidence coverage
- missing evidence is reported instead of hidden

Acceptance:

- claims receive `Supported`, `Inferred`, `Unsupported`, `Contradicted`, or `Unverified`
- failed verification degrades the RCA result instead of silently accepting bad output

## P0: Replay And Evaluation Harness

Add deterministic incident scenarios.

Initial scenario list:

- CrashLoopBackOff
- OOMKilled
- ImagePullBackOff
- readiness probe mismatch
- Service port mismatch
- bad ConfigMap rollout
- rollout latency regression
- dependency unavailable
- Prometheus unavailable
- Loki unavailable
- contradictory evidence
- irrelevant log red herrings

Metrics:

- root-cause entity accuracy
- root-cause type accuracy
- evidence precision
- evidence recall
- unsupported claim rate
- abstention quality
- investigation latency
- tool-call count
- token usage

Acceptance:

- the evaluation harness runs locally without hosted model credentials
- heuristic baseline results are recorded
- hosted provider runs can be compared without changing the scenario fixtures

## P1: Traffic And Resource Baseline Rule Packs

Add opt-in rule packs that collect richer evidence without hard-coding application metric names into controllers.

MVP signals:

- request rate change ratio
- 5xx rate
- p95 latency
- CPU throttling
- memory near limit
- timeout, retry, and rate-limit logs
- Kubernetes unhealthy events

Traffic anomaly detection should compare:

```text
current evaluation window
/
previous comparison window
>= configured ratio
```

It must also enforce a minimum current rate to avoid low-volume false positives.

Acceptance:

- query expressions are configurable through Helm values
- profiles distinguish portable Kubernetes signals from application-specific metrics
- missing Prometheus or Loki datasources degrade gracefully
- fixtures compare heuristic and hosted-provider RCA over the same evidence bundle

## P1: Bounded Agentic Investigation

Do not add unrestricted cluster agents.

Add a policy-bounded investigation loop:

```yaml
spec:
  investigationPolicy:
    adaptiveQueries: true
    allowedCapabilities:
      - kubernetes.events.read
      - kubernetes.workloads.read
      - prometheus.query
      - loki.query
    maxSteps: 8
    maxQueriesPerSource: 4
    maxDuration: 2m
    maxInputTokens: 30000
    allowCrossNamespace: false
```

Acceptance:

- adaptive queries stay inside declared capabilities
- query count, duration, and token budgets are enforced
- all adaptive evidence is recorded with provenance

## P1: Naming And API Review

Before a breaking API cut, review whether:

- `aiops.platform/v1alpha1` should move to a project-owned API group such as `fluxagent.io/v1alpha1` or `aiops.fluxseer.com/v1alpha1`
- `ModelProvider` should become `ReasoningProvider`
- `AgentAction` should become `RemediationExecution` or `ExecutionRequest`
- `InvestigationRequest.createRiskSignal` should become a clearer discovered-signal option

Acceptance:

- no rename is made casually
- migration impact is documented before changing CRDs
- old v1alpha1 semantics are preserved or explicitly migrated

## Deferred Beyond v0.3

- distributed worker pool
- multi-cluster hub/spoke
- GitOps PR backend
- approval UI
- OPA/Kyverno policy
- remediation execution breadth
- HolmesGPT/OpenSRE provider integrations
