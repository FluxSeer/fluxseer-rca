# v0.5 SRE RCA Scenario Portfolio

Status: `Active`

## Objective

Extend the current User-facing Report catalog with a small set of high-frequency
SRE incidents whose evidence can be bounded, linked, and independently
verified. This portfolio is a release-readiness slice for the v0.5 line; it is
not an attempt to enumerate every Kubernetes failure mode.

The target claim is:

> FluxSeer RCA provides trustworthy, evidence-verifiable RCA for common
> Kubernetes workload and service incidents.

The target claim is not:

```text
complete Kubernetes cluster RCA
autonomous diagnosis for every Kubernetes resource
all Kubernetes failure modes covered by User-facing Reports
```

## Strategy

Prioritize scenarios that are:

1. frequent in day-to-day SRE operations;
2. diagnosable from declared Kubernetes Events, workload status, Prometheus,
   or Loki evidence;
3. bounded enough to define a maximum supported causal claim; and
4. representative of FluxSeer RCA's evidence, policy, verification, and safe
   execution boundaries.

The number of built-in detection patterns and the number of User-facing Report
examples are intentionally separate metrics. A new pattern does not require a
new public report if it does not establish a distinct product contract, and a
public report may cover a policy, evidence, or safety state rather than a new
detection pattern.

## Release slices

| Slice | Scope | Purpose |
| --- | --- | --- |
| Before `v0.5-alpha.1` | Five RCA scenarios plus two remediation-effectiveness outcomes | Prove the high-frequency RCA and Safe Remediation contract |
| `v0.5` beta | Additional workload and service incidents selected from real replay evidence | Make the read-only RCA path useful for common SRE operations |
| `v0.6+` | Node, network, and dependency-graph investigation | Expand toward cluster-wide RCA only after the evidence model is ready |

The alpha.1 scenario slice is a companion readiness gate to the Safe
Remediation gate. It does not broaden the executor's mutation permissions or
turn every detection pattern into an acceptance case.

## Before `v0.5-alpha.1`

### 1. CrashLoopBackOff

Exercise the path:

```text
CrashLoopBackOff
-> Kubernetes Event / restart state
-> optional application log evidence
-> bounded RCA claim
```

The scenario must distinguish detection from root-cause confirmation. A
CrashLoopBackOff with no useful application log or causal evidence must finish
as `Inconclusive`, not as a specific confirmed application cause.

### 2. Readiness or liveness probe failure

Prove that `Pod Running` is not equivalent to service health. The scenario
should correlate workload status and Kubernetes event evidence and preserve a
bounded `ProbeFailure` claim without inventing the underlying application
cause.

### 3. FailedScheduling

Add one bounded scheduling cause first, such as:

- insufficient CPU or memory; or
- an untolerated node taint.

The first case does not need to model every scheduler predicate. It must make
the selected scheduling evidence and the maximum supported claim explicit.

### 4. Service port / `targetPort` mismatch

Promote the existing deterministic internal evidence path to a User-facing
case:

```text
Service port
-> targetPort
-> workload/container listener
-> mismatch
-> evidence-linked RCA
```

This is a high-value service configuration case because the conclusion is
deterministic and demonstrates evidence-backed RCA better than another
threshold-only metric case.

### 5. High HTTP error rate

Produce one complete User-facing RCA case for the existing Prometheus pattern.
The first version should correlate:

```text
Prometheus: HTTP 5xx increase
Loki or declared evidence: causal error signal
-> bounded high-error-rate RCA
```

This is not yet a general dependency graph. It only proves that a symptom from
Prometheus can be combined with causal evidence from another declared source.

### 6. Safe Remediation: `Effective`

Prove the closed loop:

```text
Incident
-> RiskSignal
-> RemediationPlan
-> Approval
-> allowlisted rolloutRestart
-> verification investigation
-> Effective
```

Execution success and incident recovery must be separate assertions.

### 7. Safe Remediation: `Ineffective`

Run the same bounded action path against a controlled target where the
post-action condition remains unhealthy. The product must report
`Ineffective` rather than treating a successful API mutation as proof that the
incident was fixed.

The `Effective` and `Ineffective` cases are remediation lifecycle scenarios,
not additional detection patterns. Their implementation and safety contract
remain governed by [v0.5 Safe Remediation](v0.5-safe-remediation.md).

## v0.5 beta follow-up

After the alpha.1 slice, select additional workload and service cases from
replay evidence rather than expanding by pattern count. Candidate areas are:

- Job and CronJob failure outcomes;
- Deployment rollout and readiness regressions;
- Service and EndpointSlice routing failures;
- DNS or upstream timeout cases where the evidence boundary is explicit;
- CPU throttling and memory-near-limit cases;
- contradictory or partial multi-source evidence.

Each candidate requires a named public contract before it is added to the
User-facing catalog. Existing internal fixtures can be promoted when their
target, evidence, expected product output, and forbidden side effects are
stable enough for public reporting.

## v0.6 and later

Defer the following until the evidence model and workload RCA boundary are
strong enough:

- Node `NotReady` and resource pressure;
- kubelet, container runtime, CNI, and network-policy diagnosis;
- PVC/PV and storage failures;
- cross-service dependency graphs and blast-radius analysis;
- multi-cluster correlation;
- broad autonomous diagnosis across non-workload resources.

These areas are intentionally not alpha.1 acceptance gates. They cross the
current workload-oriented product boundary and require more than adding a
single RiskRule or User-facing Report fixture.

## Scenario contract

Every new scenario must record:

- stable case ID and target kind;
- reproducible trigger and declared datasource inputs;
- expected terminal phase and outcome;
- maximum supported causal claim;
- evidence references and missing-evidence behavior;
- provider and datasource request expectations;
- positive and forbidden side effects;
- User-facing `fluxseer-riskrule-report/v1` output where the case is a
  product-output example;
- internal `fluxseer-test-report/v1` expected/actual assertions.

The scenario must also state whether it is:

- a detection case;
- an evidence-sufficiency case;
- a policy or infrastructure failure case; or
- a remediation-effectiveness case.

This prevents the User-facing catalog from being mistaken for a complete test
count or a complete Kubernetes analyzer inventory.

## Acceptance boundary

The alpha.1 portfolio is complete when the seven cases above have deterministic
runtime or replay evidence, stable report contracts, and no unexpected
remediation side effects outside the explicitly approved action path. The
portfolio is not blocked on Node, CNI, storage, or dependency-graph coverage.
