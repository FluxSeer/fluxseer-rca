## Artifact Identity

Status: PASS for binary metadata and OCI label identity. Published digest identity remains part of the reproducibility and release publication work.

Goal:

- make every release artifact traceable to the same Git commit
- remove `latest` as a release source of truth
- make image tag human-readable and image digest authoritative

Required release identity:

```text
tag commit
= embedded Git revision
= OCI revision label
= release notes commit
= chart appVersion
= manifests image version
= published image source commit
```

Required image reference shape:

```yaml
image:
  repository: ghcr.io/fluxseer/fluxagent
  tag: v0.2.0-beta.1
  digest: sha256:...
```

Acceptance:

- Makefile build targets accept `VERSION`, `GIT_COMMIT`, dirty-state, build-date, and image repository variables
- Go binaries expose version metadata through `version` / `version --output=json`
- operator and demo-observability images include matching binary metadata and OCI labels
- release-managed manifests can use the intended release image tag
- kind release verification can run against the intended release image reference
- `latest` is not used by release-managed paths
- digest-based release references remain pending until reproducibility and publication gates are complete

Implemented verification target:

```sh
make verify-artifact-identity
```

`verify-artifact-identity` verifies binary metadata and OCI labels. Packaging consistency is covered by `verify-packaging-consistency`.

## Build Reproducibility

Status: PASS for same-commit, same-version, same-platform local BuildKit output with provenance and SBOM disabled.

Goal:

- identify and reduce sources of image digest drift
- make release builds reproducible enough for beta release claims

Original drift from the freeze pass:

- two local rebuilds of `fluxagent/operator:latest` produced different image digests
- two local rebuilds of `fluxagent/demo-observability:latest` produced different image digests
- built images had no labels tying them to the Git commit

Potential drift sources:

- image created timestamp
- OCI provenance or attestation metadata
- Go build path
- Go build ID
- VCS metadata auto-detection
- base image tag drift
- copied file mtimes
- architecture mismatch
- dynamic build context files

Applied controls:

- base images are pinned by digest
- Docker builds use an explicit target platform
- local reproducibility builds disable BuildKit provenance and SBOM output
- `.dockerignore` excludes Git metadata, editor state, and local build/test output from the image context
- Go builds use `-trimpath` and `-buildvcs=false`
- binary mtimes are fixed from `SOURCE_DATE_EPOCH` before final image copy

Required build constraints:

- base images use digest-pinned references
- Go builds use `-trimpath`
- release build platform is explicit
- build timestamp uses commit timestamp or `SOURCE_DATE_EPOCH`, not wall-clock time
- dependencies remain locked by `go.sum`
- nonessential dynamic files are excluded from release build context

Acceptance:

- reproducibility verification compares two release image builds from the same commit
- operator and demo binaries have identical checksums across two independent builds
- operator and demo local image digests match across two no-cache BuildKit builds
- image filesystem and config differences are reported separately on failure
- reproducibility scope is limited to the same builder configuration and target platform

Implemented verification target:

```sh
make verify-build-reproducibility
```

## Lifecycle Smoke Test

Status: PASS for Helm install, upgrade, uninstall, CRD retention, and kind cluster cleanup.

Goal:

- verify install, upgrade, and uninstall behavior before beta tag
- make CRD retention behavior explicit

Minimum lifecycle gate:

```text
Fresh install
-> controller Ready
-> sample InvestigationRequest succeeds
-> Helm upgrade
-> existing CRs remain healthy
-> controller Ready again
-> uninstall
-> namespaced resources removed
-> CRD retention policy verified
-> no remaining kind cluster
```

CRD uninstall policy:

- ordinary uninstall should not accidentally delete user custom resources
- Helm installs CRDs from `charts/kube-ai-sre/crds`; Helm uninstall retains those CRDs and existing custom resources
- if CRD deletion is supported, it should require an explicit cleanup command or documented manual step
- release notes must state whether CRDs are retained or removed during uninstall
- CRD schema upgrade and migration verification is outside the `v0.2.0-beta.1` lifecycle gate

Acceptance:

- install smoke test passes in kind
- upgrade smoke test passes in kind
- uninstall smoke test passes in kind
- CRD retention or deletion policy is documented
- `kind get clusters` returns no remaining clusters after the gate

Implemented verification target:

```sh
make verify-lifecycle-kind
```

- release notes, manifest version, chart version, image labels, and embedded binary revision all point to the same commit
- only after this gate passes should `v0.2.0-beta.1` be tagged

Implemented verification target:

```sh
make verify-release-v0.2-beta VERSION=v0.2.0-beta.1 TARGET_PLATFORM=linux/amd64
```

Pre-tag assertions:

```sh
make verify-release-pretag VERSION=v0.2.0-beta.1
```

`verify-release-pretag` checks that the working tree is clean, `HEAD` matches `origin/main`, the release tag does not already exist locally or remotely, no kind cluster remains, and release test images/containers have been cleaned up.

Responsibility split:

- `verify-release-v0.2-beta` verifies the release artifacts and functional gates on a clean checkout.
- `verify-release-pretag` verifies branch synchronization and tag safety immediately before creating the annotated tag.
