# v0.5 Safe Remediation

Status: `Active`

## Objective

Prove the smallest trustworthy closed loop from an approved remediation to a
verified outcome:

```text
RiskSignal
-> RemediationPlan
-> Approval
-> AgentAction
-> Kubernetes or GitOps Executor
-> Verification Investigation
-> Effective / Ineffective / Regressed / Inconclusive
```

The product promise for v0.5 is:

> FluxSeer can safely execute an approved remediation and verify whether it
> actually fixed the incident.

This is a bounded **Safe Remediation** milestone. It is not a commitment to
make every existing executor route production-ready.

## First Checkpoint: `v0.5-alpha.1`

`alpha.1` is the smallest release that must prove the core value proposition:

```text
Approved AgentAction
        -> real allowlisted Kubernetes mutation
        -> Verification InvestigationRequest
        -> Effective / Ineffective / Regressed / Inconclusive
```

The `alpha.1` acceptance gate contains only:

1. the executor safety contract and execution state machine;
2. one real, allowlisted Kubernetes remediation path; and
3. post-action effectiveness verification.

GitOps, policy status reconciliation, and broader audit expansion remain
follow-up v0.5 work after this checkpoint. They must build on the same
contract rather than introduce a second execution model.

Batch 1 now defines `ExecutorRequest` and `ExecutorResult` in
`internal/executor`, projects the result contract into
`AgentAction.status.execution`, and keeps `ApprovedAction` as a compatibility
alias. Batch 2 now derives deterministic execution/idempotency identities and
does not re-dispatch an action whose `Executing` status already contains an
identity. Batch 3 now provides the first real
`kubernetes.rolloutRestart` Deployment path behind
`--enable-experimental-executor=true`, with target UID validation, execution
annotations, and read-after-write recovery. The remaining alpha.1 gap is
follow-up effectiveness verification; GitOps and Runbook routes remain
simulation-oriented, and successful actions are still recorded as
`status.effectiveness.phase=NotVerified`.

## In Scope

### 1. Executor safety contract

The contract and state machine are specified in
[Executor safety contract](../architecture/executor-safety-contract.md).
Implement this before adding a real Kubernetes API call.

### 2. Kubernetes executor

- implement a real backend for a small, explicitly allowlisted low-risk action
  set
- preserve dry-run and fail-closed behavior
- bind every action to an explicit target identity and precondition where the
  Kubernetes API supports one
- prevent an action from silently widening its namespace, kind, or resource
  target

### 3. GitOps executor

- implement a GitOps/PR-style backend as the preferred mutation path
- make the requested change, branch/PR identity, and resulting status
  auditable
- guarantee idempotent behavior for retries and duplicate reconciles
- do not require direct production workload mutation for the MVP

### 4. Post-action effectiveness verification

- create or link a purpose-built follow-up `InvestigationRequest` after an
  action completes
- distinguish executor success from remediation effectiveness
- persist a verification reference and a machine-readable outcome
- support `Effective`, `Ineffective`, `Regressed`, and `Inconclusive` outcomes;
  retain `NotVerified` only as a compatibility state while migration is in
  progress
- never claim that an execution succeeded merely because the incident was not
  re-observed yet

### 5. Policy status reconciler

- reconcile `ApprovalPolicy`, `NamespaceThreshold`, and `EscalationChain`
  readiness and observed generation
- surface validation errors and unsupported semantics through status
- make policy snapshots used by an action discoverable from the audit record
- keep `NamespaceThreshold.spec.protectionLevel` reserved until its enforcement
  semantics are defined

### 6. Audit trail strengthening

The durable action record must link the approval, policy decision, executor
attempts, target, action digest, execution identity, retry/timeout decisions,
and post-action verification. Kubernetes Events remain an operational aid, not
the sole audit store.

## Explicitly Deferred

The following are not v0.5 acceptance gates:

- general-purpose Runbook executor
- full multi-stage `EscalationChain` behavior (`delay`, `condition`,
  `reassign`, `auto_reject`, `force_execute`, stage-specific assignees, and
  notification templates)
- native Slack, Email, and PagerDuty receivers; generic webhook remains the
  baseline
- `NamespaceThreshold.spec.protectionLevel`
- RawSnapshot storage, encryption at rest, payload access policy,
  `DeletionPolicy`, and evidence lifecycle governance
- OpenTelemetry and CloudWatch production adapters
- runtime replay runner
- adaptive investigation runtime
- built-in alert receivers, automatic RiskSignal reinvestigation, cooldown,
  and loop-prevention workflow

These topics are staged in the v0.6-v0.8 roadmap rather than silently carried
inside the v0.5 executor milestone.

## Dependency Order

1. Freeze and implement the action safety contract and state machine.
2. Implement the Kubernetes executor behind the existing approval boundary.
3. Add baseline capture, verification-request creation, and effectiveness
   state transitions; this completes `v0.5-alpha.1`.
4. Implement the GitOps/PR executor with the same idempotency and audit
   contract.
5. Add policy CRD status reconciliation and policy snapshot references.
6. Expand audit records, integration coverage, documentation, and
   production-readiness gates.

## Definition of Done

- an approved allowlisted Kubernetes action executes against a controlled test
  target and an unapproved or tampered action is rejected
- timeout, retry, duplicate reconcile, target mismatch, policy revalidation,
  and executor failure
  cases have deterministic status and audit assertions
- execution success and effectiveness outcome are separately visible
- a follow-up verification investigation is linked to the action and can
  produce an effective, ineffective, regressed, or inconclusive result
- a GitOps action later produces an auditable, idempotent PR-style result
  without requiring direct production mutation
- all policy resources used by the completed v0.5 scope expose usable
  readiness/status information
- the default installation remains read-only and no v0.5 feature changes that
  safety boundary implicitly
- `make test`, `make lint`, Helm/Kustomize rendering, and the relevant runtime
  contract gates pass against the release candidate image
