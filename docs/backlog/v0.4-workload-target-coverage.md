# v0.4 Workload Target Coverage Gate

This ticket tracks the architecture work that moved FluxSeer RCA from
Deployment-first beta coverage toward a credible Kubernetes workload RCA
release path.

## Problem

FluxSeer RCA could support the RCA control-plane contract, but `RiskRule`
background discovery was Deployment-first. That was acceptable for a beta, but
it became a product trust problem if the project claimed broad Kubernetes RCA
while important workload controllers were outside the detection surface.

The risky failure mode is not limited coverage by itself. The risky failure
mode is producing a quiet or `NoIssueFound` result without making coverage gaps
visible.

## Goal

Before leaving beta, FluxSeer RCA should be able to claim Kubernetes workload
RCA, not full cluster-wide RCA.

Minimum credible workload coverage:

- `Deployment`
- `StatefulSet`
- `DaemonSet`
- `Job`
- `CronJob`
- Pod owner-chain resolution to a canonical workload target

Non-workload resources such as `Node`, `PVC`, `PV`, `Service`,
`EndpointSlice`, `Ingress`, `HPA`, and `PDB` may appear as evidence or root
cause entities, but they are not required as first-class discovery targets for
this gate.

## Product Boundary

Allowed claim after this ticket:

```text
Kubernetes workload RCA
```

Still not allowed:

```text
complete Kubernetes cluster RCA
cluster-wide RCA coverage
autonomous Kubernetes diagnosis for every resource kind
```

Docs, release notes, README, and GitHub repo metadata must continue to state
coverage boundaries explicitly.

## Architecture

Do not create separate controllers for each workload kind.

Keep the top-level flow:

```text
RiskRule
-> discover target
-> normalize target
-> run signals
-> create InvestigationRequest
-> collect evidence
-> verify RCA
```

Introduce an internal workload target abstraction:

```go
type WorkloadTarget struct {
    Resource   domain.ResourceRef
    UID        string
    Generation int64
    Labels     map[string]string
    Pods       []PodReference
    Status     WorkloadStatus
    OwnerChain []domain.ResourceRef
}
```

Introduce resolver implementations behind one registry:

- `DeploymentResolver`
- `StatefulSetResolver`
- `DaemonSetResolver`
- `JobResolver`
- `CronJobResolver`
- `PodOwnerResolver`

`RiskRuleReconciler` should depend on the resolver registry, not on
Deployment-specific list logic.

## Model Reuse

Reuse the existing public models where possible:

- `RiskRule.spec.targetSelector`
- `RiskRule.spec.signals`
- `RiskRule.spec.investigationPolicy`
- `InvestigationRequest.spec.target`
- `InvestigationRequest.status.verdict`
- `InvestigationRequest.status.claims`
- `InvestigationRequest.status.evidenceRefs`
- `InvestigationRequest.status.evidenceCoverage`
- `InvestigationRequest.status.lineage`
- `TargetRef`
- `domain.ResourceRef`
- datasource `QueryRequest`, `QueryResult`, and `Capabilities`

Do not introduce new public CRDs for each workload kind.

## Required Runtime Work

- Replace Deployment-only `RiskRule` target discovery with workload resolver
  registry discovery.
- Support `StatefulSet`, `DaemonSet`, `Job`, and `CronJob` as canonical
  `InvestigationRequest.spec.target` kinds.
- Resolve Pod events to the owning canonical workload when possible:
  - Pod -> ReplicaSet -> Deployment
  - Pod -> StatefulSet
  - Pod -> DaemonSet
  - Pod -> Job
  - Job -> CronJob when applicable
  - ownerless Pod remains a Pod target
- Preserve stable finding identity across pod churn and workload rollouts.
- Keep `RiskRule -> InvestigationRequest` as the preferred path.
- Keep `DirectRiskSignal` as a compatibility path only.

## Evidence Work

Generalize Deployment-specific Kubernetes evidence without breaking existing
contracts:

- keep `deploymentCondition` as a compatibility query type
- add or internally map to workload-oriented status evidence
- collect workload events through owner-aware target matching
- collect related pod status evidence for canonical workload targets
- allow non-workload resources to appear as evidence or
  `verdict.rootCauseEntity`

## Coverage Visibility

Add explicit coverage reporting so users do not confuse partial coverage with
cluster health.

Target status shape:

```yaml
status:
  coverage:
    supportedTargetKinds:
      - Deployment
      - StatefulSet
      - DaemonSet
      - Job
      - CronJob
    unsupportedDiscoveredKinds:
      Node: 6
      PersistentVolumeClaim: 18
    partial: true
```

Exact schema can change during v0.4 design, but the release must expose:

- supported target kinds
- unsupported discovered kind counts
- partial coverage flag
- condition reason when coverage is intentionally incomplete

## Acceptance Criteria

- `RiskRule` can discover and route matches for `Deployment`,
  `StatefulSet`, `DaemonSet`, `Job`, and `CronJob`.
- Pod-level events are attributed to a stable canonical workload target when
  an owner chain exists.
- Reconciles do not create unbounded investigations for pod UID churn.
- `InvestigationRequest` can complete RCA for each supported workload kind
  through the canonical status contract.
- `status.evidenceCoverage` and rule coverage status make unsupported
  resources visible.
- Built-in rule packs can be scoped across selected namespaces and all
  namespaces without implying complete cluster coverage.
- Query budget and result limit behavior is tested against multi-kind,
  multi-namespace rule packs.
- README and product docs distinguish:
  - Deployment-first beta coverage
  - Kubernetes workload RCA
  - future cluster infrastructure RCA

## Test Requirements

- unit tests for each workload resolver
- unit tests for pod owner-chain canonicalization
- envtest coverage for multi-kind discovery
- controller tests for `RiskRule -> InvestigationRequest` routing by kind
- replay fixtures for:
  - StatefulSet pod OOM
  - DaemonSet unavailable on selected nodes
  - Job failed
  - CronJob-created Job failed
  - Deployment CrashLoopBackOff regression
- regression test that unsupported resource kinds are surfaced in coverage
  status instead of being silently ignored

## Exit-Beta Gate

This is an exit-beta blocker if the project wants to market itself as
Kubernetes workload RCA.

The project can leave beta only if one of these is true:

1. this ticket is implemented and verified, or
2. all public positioning remains explicitly Deployment-first and the release
   does not claim Kubernetes workload RCA.

Full cluster infrastructure RCA remains a later milestone after workload RCA
is credible.

## Implementation Checkpoint

Implemented:

- `RiskRule` target discovery now supports `Deployment`, `StatefulSet`,
  `DaemonSet`, `Job`, `CronJob`, and `Pod`.
- Pod discovery canonicalizes owner chains for:
  - Pod -> ReplicaSet -> Deployment
  - Pod -> StatefulSet
  - Pod -> DaemonSet
  - Pod -> Job
  - Job -> CronJob lineage metadata
- `InvestigationRequest` target resolution now accepts `Job` and `CronJob`.
- Kubernetes datasource `deploymentCondition` remains a compatibility query
  type and now returns workload-status records for supported non-Deployment
  workload kinds.
- Kubernetes event matching now considers related Pods selected by workload
  labels so pod-level events can support canonical workload RCA.
- `RiskRule.status.coverage` reports supported target kinds, unsupported
  selected resource-kind counts, and partial coverage.
- Default RBAC now grants read access to `batch/jobs` and `batch/cronjobs`.
- Focused unit and controller coverage exists for multi-kind discovery, Pod
  owner canonicalization, unsupported-kind coverage status, and `StatefulSet`,
  `DaemonSet`, `Job`, and `CronJob` `RiskRule -> InvestigationRequest`
  routing.
- Raw-to-final replay fixtures cover StatefulSet OOMKilled, DaemonSet BackOff,
  Job BackOff, and CronJob-created workload BackOff scenarios.
- Helm rule-pack rendering validation covers multi-kind workload selectors.
- Product docs distinguish implemented workload RCA from future full cluster
  infrastructure RCA.

Gate status:

```text
Closed for Kubernetes workload RCA positioning.
Full cluster infrastructure RCA remains out of scope.
```
