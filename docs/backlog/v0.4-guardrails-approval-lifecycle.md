# v0.4 Guardrails and Approval Lifecycle

This ticket tracks the first implementation batch of the `v0.4` focus area
described in [ROADMAP.md](../../ROADMAP.md): "guardrails and approval
lifecycle... explicit policy decisions and approval requests... approval
timeout and escalation behavior... richer audit persistence and status
transitions."

Status: complete. The API, controller lifecycle, notifier retry behavior,
audit timestamps, CRD synchronization, and focused regression tests are
implemented. The maintained verification entrypoint is:

```sh
make verify-v0.4-approval-lifecycle
```

`RemediationPlan` and `AgentAction` are "Guarded experimental" per
[docs/capability-maturity.md](../capability-maturity.md): controllers and RBAC
are disabled by default (`features.remediation.enabled=false`). This ticket
stays inside that boundary. Nothing here changes the default installation.

## Problem

The `RiskSignal -> RemediationPlan -> AgentAction` chain already has a working
policy engine (`internal/guardrails`) and a deliberately tamper-resistant
approval handoff (digest-bound approval in `AgentActionReconciler`). But
auditing the reconcile loop surfaced three gaps, two of which are correctness
bugs, not missing features:

1. **No approval timeout or escalation.** Once an `AgentAction` reaches
   `WaitingApproval`, `AgentActionReconciler` returns `ctrl.Result{}` with no
   `RequeueAfter`. Nothing ever revisits it. An action can sit unapproved
   indefinitely with no notification that it is stuck. This is the actual
   `v0.4` feature gap.

2. **`RemediationPlanReconciler` re-decides on every reconcile instead of
   once.** It recomputes `guardrails.Engine.Evaluate(...)` and unconditionally
   overwrites both `plan.Status` and the owned `AgentAction.Status` every time
   it runs, including timestamps. Because it `Owns(&v1alpha1.AgentAction{})`
   with no predicate, *any* status change on the child `AgentAction` (moving
   to `Executing`, `Succeeded`, our new `Escalated`, ...) re-triggers
   `RemediationPlanReconciler`, which then stamps a fresh `metav1.Now()` on
   `plan.Status` and re-derives `AgentAction.Status` from scratch. Two
   consequences:
   - A `RemediationPlan` reconciles itself in a permanent loop in a live
     cluster: `UpdatedAt` differs on every pass, so `statusChangedPlan` is
     always true, so it always writes, so the write always re-triggers itself
     via its own `For(&v1alpha1.RemediationPlan{})` watch.
   - Worse, every one of those passes re-derives the `AgentAction` decision
     from the immutable spec (still `ApprovalManual`, say) and overwrites
     `AgentAction.Status` back toward `WaitingApproval` /
     `ManualApprovalRequired` -- including after the action has already
     executed. This is silent, timing-dependent status corruption of a
     resource this project explicitly designs to be tamper-evident.

3. **`AgentActionReconciler`'s "not yet approved" branch is not safe to
   re-run while legitimately pending.** `isAgentActionApproved` only returns
   true once `spec.approvedBy` is set. Until then, every reconcile of a
   correctly-`WaitingApproval` action falls into the `!isAgentActionApproved`
   branch, which unconditionally resets `status.approval.source` to
   `"Pending"` -- discarding the `"ManualApprovalRequired"` marker
   `RemediationPlanReconciler` recorded. `isAgentActionApproved`'s manual path
   only honors `source == "ManualApprovalRequired"`, so once downgraded to
   `"Pending"`, a human setting `spec.approvedBy` can never approve the action
   again. Today this is dormant because nothing revisits a pending
   `AgentAction` before a human acts on it except the controller-runtime
   default cache resync (many hours). A timeout/requeue mechanism -- item 1 --
   would revisit it constantly and turn this into an immediate, reliable
   break of the approval path.

Item 1 cannot be built correctly on top of items 2 and 3 left as-is: the
escalation status would either get silently reverted by
`RemediationPlanReconciler`, or the requeue needed to check the deadline
would itself strip the action's ability to ever be approved.

## Goal

- `AgentAction`/`RemediationPlan` support an opt-in
  `spec.approvalTimeoutSeconds`. Zero/unset means no behavior change (fully
  backward compatible with existing manifests).
- An unapproved `AgentAction` past its deadline transitions to a new
  `Escalated` phase exactly once and fires one notification through the
  existing `internal/notifier` abstraction (the same one
  `RiskSignalNotificationReconciler` and `NotificationExecutor` already use --
  no new notification channel).
- `RemediationPlanReconciler` decides a plan/action's initial approval
  disposition exactly once and never overwrites subsequent state that
  `AgentActionReconciler` owns.
- A pending `AgentAction` can always still be approved by a human no matter
  how many times it gets reconciled while waiting.

## Non-Goals

- No auto-reject or auto-execute on timeout. Escalation only notifies; a
  human (or an explicit future policy) still decides. This matches the
  project's fail-closed, human-in-the-loop default.
- No new CRD. `approvalTimeoutSeconds` is a field on the existing
  `RemediationPlan`/`AgentAction` contracts.
- No change to the default Helm installation posture. Remediation controllers
  remain opt-in via `features.remediation.enabled`.
- Not wiring `approvalTimeoutSeconds` through `RiskRule` ->
  `RiskSignal` generation (`riskrule_controller.go`,
  `deployment_risk_controller.go`) in this batch. Both currently construct
  `RiskSignalSpec` without it, same as they do for other opt-in knobs; adding
  a per-rule timeout policy is a reasonable follow-up but is a separate,
  `RiskRule`-schema-shaped decision. `RiskSignalSpec.approvalTimeoutSeconds`
  is still added so the field flows end-to-end for direct/GitOps-authored
  `RiskSignal` and `RemediationPlan` objects (the same compatibility path
  `RiskSignal` already supports per
  [docs/capability-maturity.md](../capability-maturity.md)).
- Not touching `internal/audit.Store`. It is in-memory, unpersisted, and
  already used for an unrelated purpose (investigation tracing); it is not
  the right foundation for approval audit history. Durable approval history
  for this batch is the CRD `status` transition itself
  (`phase`, `approval.escalatedAt`, ...). Kubernetes `Event` emission for a
  human-visible `kubectl describe` timeline is worth a follow-up batch but is
  not required for the timeout/escalation mechanism to work correctly, so it
  is left out here to keep this change reviewable.

## Architecture

Keep the existing three-controller shape
(`RiskSignalReconciler` -> `RemediationPlanReconciler` -> `AgentActionReconciler`).
No new controller.

`RemediationPlanReconciler`:

- Add a top-of-`Reconcile` guard: if `plan.Status.Phase != ""`, return
  immediately. The plan's approval decision is derived once, at creation,
  from an immutable spec; there is no legitimate reason to re-derive it later,
  and doing so is exactly what caused problems 2 above.

`AgentActionReconciler`:

- Split the "not yet approved" branch in two:
  - "Never validly evaluated" (`status.approval == nil` or digest mismatch):
    keep today's behavior, reset to `Pending` / `WaitingApproval`. This is
    the attacker/tampered-action case and must stay fail-closed.
  - "Correctly pending, digest still valid, just waiting on a human": leave
    `status.approval` untouched (preserves `"ManualApprovalRequired"`) and
    run the new timeout check instead of unconditionally rewriting status.
- New timeout check compares `now()` against `status.updatedAt` (the
  timestamp already recorded when the action first entered `WaitingApproval`)
  plus `spec.approvalTimeoutSeconds`:
  - Deadline not reached: return `ctrl.Result{RequeueAfter: remaining}`
    without writing anything, so `status.updatedAt` stays anchored to the
    original wait-start time instead of sliding forward.
  - Deadline reached and not already `Escalated`: notify first, and only
    persist the `Escalated` phase / `status.approval.escalatedAt` after the
    notifier call succeeds (mirrors `RiskSignalNotificationReconciler`'s
    notify-then-mark-done ordering, so a failed webhook delivery is retried
    on the next reconcile instead of being silently lost).
  - Already `Escalated`: no-op. A human approving afterward still works
    normally since `source` was never changed away from
    `"ManualApprovalRequired"`.

## Required Runtime Work

- `api/v1alpha1`: add `PhaseEscalated`; add `ApprovalTimeoutSeconds` to
  `RiskSignalSpec`, `RemediationPlanSpec`, `AgentActionSpec`; add
  `EscalatedAt *metav1.Time` to `AgentActionApprovalStatus`; extend
  `AgentAction.DeepCopyInto` for the new pointer field.
- `internal/controllers`: the `RemediationPlanReconciler` and
  `AgentActionReconciler` changes described above; propagate
  `approvalTimeoutSeconds` `RiskSignal -> RemediationPlan -> AgentAction` the
  same way `ttlSeconds` already propagates.
- `internal/operatorapp`: wire an optional `notifier.Notifier` into
  `AgentActionReconciler` (reuse `FLUXSEER_RCA_WEBHOOK_URL`, same as the
  existing `RiskSignalNotificationReconciler` wiring).
- `config/crd/bases` and `charts/fluxseer-rca/crds`: add the new spec/status
  fields, kept byte-identical (`make verify-v0.3-beta-hardening` diffs them on
  every CI run).

## Schema Freeze Interaction

`hack/verify-v0.3-schema-freeze.sh` fails closed if `api/v1alpha1` or
`config/crd/bases` differ from the `v0.3.0-beta.1` tag. That check only runs
from `verify-release-v0.3-beta` (release-tagging time), not from the
per-push `verify-v0.3-beta-hardening` CI gate, so this change does not break
regular CI. It does mean the next `make verify-release-v0.3-beta` run will
fail by design: that failure is the intended signal that the API has moved
past the frozen `v0.3` contract. Retiring or re-anchoring that freeze script
to a new tag is a release-process decision for whoever cuts the next release
line, not part of this ticket.

## Acceptance Criteria

- Setting `approvalTimeoutSeconds` on an `AgentAction` (directly, or via
  `RemediationPlan`/`RiskSignal`) that stays unapproved past the deadline
  moves it to `Escalated` exactly once and calls the configured notifier
  exactly once.
- Leaving `approvalTimeoutSeconds` unset/zero reproduces today's behavior
  exactly (no requeue, no escalation) -- existing manifests are unaffected.
- A human can still approve an `AgentAction` (via `spec.approvedBy`) after
  any number of reconciles while it was `WaitingApproval`, and after it has
  escalated.
- After an `AgentAction` reaches `Succeeded`, `Failed`, or `Rejected`,
  no later reconcile of its owning `RemediationPlan` changes its status
  again.
- A failed notifier call during escalation does not get silently dropped: the
  action stays eligible for the next reconcile to retry the notification.
- `go test ./...` stays green; `config/crd/bases` and
  `charts/fluxseer-rca/crds` stay diff-identical.

## Test Requirements

- Regression test: after `AgentActionReconciler` marks an action `Succeeded`,
  re-running `RemediationPlanReconciler.Reconcile` on the owning plan leaves
  the action's status untouched.
- Regression test: an `AgentAction` reconciled multiple times while validly
  `WaitingApproval` (digest unchanged, no approval yet) can still be approved
  by setting `spec.approvedBy` afterward.
- Timeout test (fake clock): before the deadline, `Reconcile` returns a
  `RequeueAfter` and does not change phase; at/after the deadline, phase
  becomes `Escalated`, `status.approval.escalatedAt` is set once, and the
  test notifier records exactly one call.
- Notifier-failure test: a notifier that returns an error leaves the action
  out of `Escalated` and `Reconcile` returns an error (so it gets retried).
- Tampered/never-evaluated actions still reset to `Pending` /
  `WaitingApproval` exactly as before (existing tests in
  `controllers_test.go` must keep passing unmodified).
