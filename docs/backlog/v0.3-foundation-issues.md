# v0.3 Foundation Issues

This backlog turns the `v0.3` trustworthy RCA direction into implementation-sized issues.

Recommended order:

```text
1 -> 3 -> 4 -> 2 -> 7 -> 5 -> 6 -> 8
```

The intent is to harden `InvestigationRequest` evidence and RCA contracts before routing background `RiskRule` detections into that workflow.

## Milestones

### M1: Contract Foundation

```text
#1 normalized observation
#3 structured RCA status
#4 heuristic verifier
#2 RiskRule routing
```

Exit criteria:

```text
RiskRule
-> InvestigationRequest
-> observations
-> provider-neutral RCA
-> verification
-> optional discovered RiskSignal
```

The path has deterministic IDs, lineage, deduplication, and degraded semantics.

### M2: Replay Harness

Build contract fixtures before adding richer rule packs:

```text
observation bundle
-> expected claims
-> expected verification
-> expected outcome
```

Hosted provider tests should validate parser and contract behavior without making paid API calls.

### M3: Rule Packs

Add opt-in profiles after the observation and RCA contracts are stable:

```text
trafficAnomaly
resourceContention
```

Both profiles should default to disabled because metric names and label shapes are not portable.

### M4: Migration Guide

Publish the migration guide after the feature contracts settle. Each feature PR should still update its reference docs as it lands.

## Issue 1: `feat: add normalized observation contract`

Define the provider-bound evidence layer.

Required distinction:

```text
Raw Evidence
-> Normalized Observation
-> Evidence Reference
```

- Raw Evidence: adapter output; only in memory or a controlled evidence store.
- Normalized Observation: redacted, truncated, normalized, and safe for reasoning and verification.
- Evidence Reference: compact status reference persisted to CRD status.

Proposed model:

```go
type Observation struct {
    ID               string
    SchemaVersion    string
    DataSourceRef    ObjectReference
    Capability       Capability
    QueryDigest      string
    TimeRange        TimeRange
    Type             ObservationType
    Value            ObservationValue
    ContentDigest    string
    RedactionProfile string
    Truncated        bool
    OriginalCount    int
    RetainedCount    int
    CollectedAt      time.Time
}
```

`ObservationValue` should be a typed union, not `map[string]any`:

- `MetricObservation`
- `LogObservation`
- `EventObservation`
- `DeploymentConditionObservation`

Digest contract:

```text
queryDigest   = canonicalized query + datasource capability
contentDigest = canonicalized redacted observation
```

Acceptance:

- deterministic canonical serialization
- stable observation ID
- schema version recorded
- evidence references cannot point to missing observations
- redaction happens before `contentDigest`
- truncation records original and retained counts
- CRD status stores compact references, not large timeseries or log bodies

## Issue 3: `feat: add provider-neutral structured RCA status`

Add the structured `InvestigationRequest.status` contract before routing more producers into it.

This issue owns the domain types, CRD status shape, enum values, compatibility fields, and derivation rules. Provider-specific response conversion belongs to provider adapter conformance and replay tests, not this issue.

Required lifecycle fields:

```yaml
status:
  observedGeneration: 3
  phase: Completed
  outcome: Confirmed
```

Semantic split:

- `phase`: workflow lifecycle.
- `outcome`: RCA result such as `Confirmed`, `Inconclusive`, or `NoIssueFound`.
- `conditions`: stage status for evidence, reasoning, verification, notification, and promotion.

Execution metadata:

```yaml
execution:
  providerRef:
    name: claude-prod
    generation: 4
  providerType: Anthropic
  model: claude-sonnet-...
  reasoningPolicyVersion: rca-v3
  controllerVersion: v0.3.0
  attempts: 1
  durationSeconds: 4
```

Confidence:

```yaml
confidence:
  providerScore: 0.91
  verifiedScore: 0.74
  level: Medium
  method: EvidenceCoverageV1
```

Compatibility fields:

- keep `summary`, `hypothesis`, `provider`, and compatibility confidence fields in `v0.3`
- derive them from structured RCA fields
- do not remove them before `v1beta1`

Acceptance:

- `InvestigationRequest.status` is the canonical RCA result
- all providers normalize into the same status shape
- compatibility fields are populated from structured fields
- `InvalidProviderResponse` is surfaced when hosted output cannot normalize
- `Inconclusive` is representable without failing the workflow

## Issue 4: `feat: add heuristic claim verifier`

Add a deterministic verifier that checks provider claims against observations.

Claims need a structured type:

```yaml
claims:
  - id: claim-001
    type: TrafficIncrease
    statement: Request rate increased 4.8x.
    evidenceRefs:
      - prom-request-rate
```

Initial claim-to-observation mapping:

| Claim type | Supporting observations |
| --- | --- |
| `TrafficIncrease` | metric |
| `CPUThrottling` | metric |
| `CrashLoop` | event, deployment-condition |
| `ImagePullFailure` | event, deployment-condition |
| `TimeoutPattern` | log |
| `DeploymentUnavailable` | event, deployment-condition |

Verifier responsibilities:

- evidence reference exists
- capability supports claim type
- time ranges overlap
- evidence is not too heavily truncated for the claim strength
- claims without evidence are not marked supported
- provider confidence is capped by evidence coverage
- `Contradicted` only for directly comparable structured cases

If verification is incomplete:

```yaml
phase: Completed
outcome: Inconclusive
conditions:
  - type: RCAReady
    status: "True"
  - type: Verified
    status: "False"
    reason: InsufficientEvidence
  - type: Degraded
    status: "True"
```

Acceptance:

- verifier returns `Supported`, `Inferred`, `Unsupported`, `Contradicted`, or `Unverified`
- unsupported claims do not appear as verified root causes
- provider success and verification quality remain separate status dimensions

## Issue 2: `feat: route RiskRule matches through InvestigationRequest`

Route background detections into the stabilized investigation workflow.

Avoid AI-specific naming. Use investigation-oriented policy:

```yaml
spec:
  investigationPolicy:
    mode: CreateRequest
    createRiskSignal: false
```

Compatibility path:

```yaml
spec:
  investigationPolicy:
    mode: DirectRiskSignal
```

Initial default should remain `DirectRiskSignal` so beta users do not see surprise behavior changes. `v0.3` docs should recommend `CreateRequest` after the contract is stable.

Idempotency key:

```text
RiskRule UID
+ RiskRule generation
+ target UID
+ normalized window bucket
+ finding fingerprint
```

Lineage:

```yaml
status:
  lineage:
    source:
      apiVersion: aiops.platform/v1alpha1
      kind: RiskRule
      namespace: prod
      name: traffic-anomaly
      uid: ...
      generation: 3
    targetUID: ...
    findingFingerprint: sha256:...
    investigationDepth: 0
```

Discovered `RiskSignal` objects created by the request should carry:

```yaml
metadata:
  annotations:
    fluxagent.io/discovered-by-investigation: investigate-checkout
```

Acceptance:

- same rule, target, window bucket, and fingerprint do not create duplicate requests
- direct `RiskSignal` compatibility path still works
- `CreateRequest` path creates an `InvestigationRequest` with lineage
- discovered signals do not trigger reinvestigation unless explicit policy opts in
- no reconcile timestamp is used in the idempotency key

## Issue 5: `feat: add traffic anomaly rule pack`

Add an opt-in profile for traffic changes after observation contracts are stable.

Default:

```yaml
rulePacks:
  trafficAnomaly:
    enabled: false
```

Signals:

- request rate change ratio
- 5xx rate
- p95 latency

Anomaly config:

```yaml
rulePacks:
  trafficAnomaly:
    anomaly:
      evaluationWindow: 10m
      comparisonWindow: 30m
      increaseRatio: 3.0
      minimumCurrentRate: 10
```

Acceptance:

- query expressions are configurable through Helm values
- metric names are not hard-coded in controllers
- missing Prometheus datasource degrades gracefully
- low-volume ratio spikes are suppressed by `minimumCurrentRate`
- fake observability includes a traffic surge fixture
