# v0.2 Beta Backlog

This backlog tracks the next hardening work after `v0.2.0-alpha.2`.

## Provider Response Governance Hardening

Status: first hardening batch complete on `main` after `v0.2.0-alpha.2`.

Goal:

- validate hosted provider responses before persisting RCA fields
- make malformed, incomplete, or non-JSON responses produce clear degraded conditions
- keep provider output execution-blind and read-only

Acceptance:

- tests cover malformed JSON, missing required fields, empty response bodies, and unsupported response shapes
- `RCAReady=False` exposes a stable reason such as `InvalidProviderResponse`
- no raw provider payload or secret material is persisted into CRD status

Completed:

- hosted provider structured responses reject missing `confidenceScore`
- structured responses reject empty or missing `rcaCauses`
- reasoning engine validates all provider `ModelResponse` values before deriving RCA fields
- tests cover incomplete hosted OpenAI content and invalid custom provider responses

Remaining:

- extend adapter tests for empty hosted-provider response bodies across OpenAI, Claude, and Gemini
- add broader malformed response-shape matrix per hosted provider
- review CRD status messages for provider payload truncation and secret safety

## Adapter Auth, Retry, And Backoff Hardening

Goal:

- standardize auth, timeout, retry, and backoff behavior across datasource adapters
- make optional integration failures visible without crashing reconciliation

Acceptance:

- Prometheus and Loki adapters have explicit timeout and retry behavior
- auth and connectivity failures map to stable degraded reasons
- tests cover transient failures, permanent auth failures, and partial-evidence behavior

## Bedrock Provider Readiness Boundary

Goal:

- either promote Bedrock from scaffold to a minimally runnable hosted provider path or document it as scaffold-only

Acceptance:

- if promoted: runtime config, secret handling, timeout behavior, and response validation are tested
- if left scaffolded: README, adapter docs, and release notes clearly state the boundary
- provider matrix does not imply production readiness beyond implemented behavior

## v0.2 Beta Release Gate Definition

Goal:

- define the minimum validation and documentation bar for `v0.2.0-beta.1`

Acceptance:

- release gate lists required local, kustomize, and kind validations
- non-goals remain explicit around autonomous remediation
- release notes and checkpoint use the same product status language
- beta claims do not exceed verified behavior
