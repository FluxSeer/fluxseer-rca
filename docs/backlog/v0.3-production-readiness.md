# v0.3 Production Readiness Backlog

This backlog records the production-readiness hardening tickets that must be resolved before calling the `v0.3` RCA contract stable.

The foundation work in [v0.3 Foundation Issues](v0.3-foundation-issues.md) established the first canonical path:

```text
RiskRule
-> InvestigationRequest
-> normalized observations
-> provider-neutral RCA
-> heuristic verification
-> optional materialized RiskSignal
```

This document tracks the next gate: making that path dependable under repeated reconcile, partial evidence, provider retries, status conflicts, bounded storage, and security constraints.

## Cross-Ticket Definition Of Done

Every production-readiness ticket should preserve these invariants:

- v0.2 compatibility fields such as `status.summary`, `status.hypothesis`, `status.confidence`, and `status.provider` remain projections from canonical status during migration.
- compatibility fields are not independent truth.
- new persisted contracts carry version metadata where relevant, including RCA schema version, canonicalization version, reasoning policy version, verifier version, controller version, and provider configuration generation.
- status writes use an explicit optimistic-concurrency strategy: patch or update behavior, conflict reload, mergeable fields, attempt append behavior, and checkpoint transition preconditions must be documented.
- exactly-once provider execution is not claimed. FluxAgent should guarantee persisted-completion idempotency: a completed execution with a durable provider result is not executed again. If the controller crashes after provider success but before checkpoint persistence, duplicate provider requests may still occur unless the provider supports and honors an idempotency key.

## P0-1: Formal Status Semantics

Define the status dimensions without mixing workflow lifecycle and RCA conclusion.

Required split:

```yaml
status:
  phase: Completed
  outcome: Confirmed
  failure: null
  degradation:
    degraded: false
  conditions: []
```

Target fields:

| Field | Purpose |
| --- | --- |
| `phase` | Workflow lifecycle. |
| `outcome` | RCA conclusion. |
| `failure` | Workflow failure details when the workflow cannot complete. |
| `degradation` | Capability loss during execution. |
| `conditions` | Stage health and readiness. |

Candidate `phase` values:

```text
Pending
Collecting
Reasoning
Verifying
Completed
Failed
```

Candidate `outcome` values:

```text
Confirmed
Inconclusive
NoIssueFound
Unknown
```

`ExecutionFailed` should not be an RCA outcome. Workflow failures should be represented through `status.phase=Failed`, `status.outcome=Unknown`, and `status.failure`.

Acceptance:

- `outcome` only describes RCA conclusions.
- `phase` only describes workflow lifecycle.
- `Observed` is replaced or explicitly deprecated.
- `ExecutionFailed` is removed from the target RCA outcome enum.
- `status.failure` includes `code`, `message`, `stage`, and `retryable`.
- `status.observedGeneration` is always populated when status is written.
- non-terminal phases omit `outcome` or leave it unset; `Unknown` is reserved for terminal failure.
- non-terminal phases do not retain stale terminal outcome, failure, or completed-at fields.
- `failure.code` uses a stable enum; `failure.message` is the human-readable free-text field.
- `failure` is absent unless `phase=Failed`.
- degradation is orthogonal to phase and outcome; `Completed + Confirmed + degraded=true` is a legal state.
- `degradation.reasons[]` uses structured code, stage, and datasource or provider references.
- `conditions` are Kubernetes-style projections for consumers, not the canonical state machine.
- documentation lists legal terminal combinations:
  - `Completed + Confirmed`
  - `Completed + Inconclusive`
  - `Completed + NoIssueFound`
  - `Failed + Unknown + failure`
- `Completed + NoIssueFound` requires the P0-13 evidence profile gate.
- tests cover success, inconclusive, no issue found, and failed execution paths.

## P0-2: Durable Provider Execution Checkpoint

Prevent repeated hosted-provider calls when reconciliation or status persistence is retried.

Problem:

```text
provider call succeeds
-> status patch conflicts
-> provider result is not durable
-> next reconcile calls provider again
```

Target checkpoint:

```yaml
status:
  execution:
    id: sha256:...
    state: ProviderCompleted
    providerResult:
      schemaVersion: fluxagent-rca-result-v1
      digest:
        algorithm: sha256
        canonicalization: fluxagent-rca-json-v1
        value: sha256:...
      normalizedResult: {}
```

Acceptance:

- `ProviderCompleted` is set only after the normalized provider result is durably persisted.
- same completed `execution.id` reuses the persisted result.
- verifier can rerun from the persisted provider result without another provider call.
- status conflict retry does not rerun external provider side effects.
- docs call this guarantee persisted-completion idempotency, not exactly-once external provider invocation.
- the unavoidable crash window is documented: provider success before checkpoint persistence can still lead to a duplicate provider request if provider-side idempotency is unavailable.
- provider result persistence stores normalized common RCA result, not raw provider response.
- raw provider response, chain-of-thought, full prompts, and unclassified provider metadata are not persisted by default.
- checkpoint state transitions are defined at least as `NotStarted -> AttemptPrepared -> ProviderInFlight -> ProviderCompleted -> Verified -> Finalized`.
- `ProviderCompleted` is not written merely because HTTP returned 200; parsing, normalization, validation, and persistence must succeed first.
- tests simulate provider success followed by status update conflict.
- docs state that `InvestigationRun` is a possible future child resource, but not required for the first v0.3 hardening cut.

## P0-3: Execution / Attempt / Provider Request Identity

Separate logical execution identity from retry attempts and provider-side request identity.

Target model:

```yaml
execution:
  id: sha256:logical-execution
  attempts:
    - id: attempt-001
      providerRequestID: req_xxx
      result: TimedOut
    - id: attempt-002
      providerRequestID: req_yyy
      idempotencyKey: sha256:...
      retryReason: PreviousAttemptTimedOut
      result: Completed
```

Definitions:

| Identity | Meaning |
| --- | --- |
| `execution.id` | Logical input identity. |
| `attempt.id` | One FluxAgent attempt for the logical execution. |
| `providerRequestID` | Provider-side request ID when available. |

Acceptance:

- `execution.id` is derived from request UID, spec generation, target UID, target observed generation, evidence bundle digest, provider type, provider configuration generation, model, reasoning policy version, and RCA schema version.
- same completed `execution.id` reuses the persisted result.
- same `execution.id` with incomplete attempts follows retry policy.
- `attempt.id` is generated by FluxAgent and does not depend on provider response.
- attempts record `startedAt`, `completedAt`, result, retry reason, and provider request ID when available.
- optional provider idempotency keys are generated by FluxAgent and sent only when the provider supports them.
- provider request IDs are stored when adapters expose them.
- provider request IDs are used for correlation, provider support, audit, and cost investigation; they are not execution identity.
- docs state that hosted LLMs do not guarantee deterministic output for identical logical input.

## P0-9: DataSource Network Safety Policy

Prevent SSRF while still allowing legitimate cluster-private observability endpoints.

Rules:

- metadata endpoints are always denied
- loopback and link-local addresses are denied by default
- private networks are allowed only by allowlist or namespace policy
- public endpoints are governed by datasource and provider data policy
- redirects are revalidated after DNS and IP resolution

Target policy:

```yaml
networkPolicy:
  allowedHosts:
    - "*.monitoring.svc.cluster.local"
    - "*.logging.svc.cluster.local"
  allowedCIDRs:
    - 10.32.0.0/16
  deniedCIDRs:
    - 169.254.169.254/32
```

Acceptance:

- tests reject metadata endpoint access
- tests reject redirect-to-metadata
- tests allow configured cluster service endpoints
- DNS rebinding is addressed by resolving and checking all A and AAAA records, pinning connection targets to verified IPs, and retaining the original hostname for TLS SNI where needed
- IPv6 loopback, link-local, IPv4-mapped IPv6, and metadata routes are handled
- every redirect hop repeats scheme, host, port, DNS, and CIDR policy checks
- environment proxy behavior is explicit: disabled by default or limited to controlled proxy configuration
- HTTP clients enforce timeout and maximum response size
- implemented status: datasource clients now validate endpoint and redirect targets, deny metadata/loopback/link-local/unspecified IPs, require `allowedCIDRs` for private IP endpoints, allow cluster service hostnames, disable environment proxy use, resolve datasource hostnames through a policy-aware dialer, validate all resolved A/AAAA addresses, and pin TCP connections to verified IPs. Redirect rejection diagnostics include the redirected host, resolved-IP diagnostics include host and denied IP, and tests cover IPv6 loopback/link-local/unspecified addresses, IPv6 metadata routes, IPv4-mapped metadata addresses, redirect-to-metadata, redirect host allowlist rejection, mixed allowed/denied DNS answers, and cluster service private IP allowance.

## P0-10: Query Budget Policy

Protect Prometheus, Loki, and FluxAgent from expensive user-configured queries.

Policy is split into two layers:

Pre-query policy:

- max time range
- query syntax policy
- allowed functions
- regex restrictions
- timeout

Post-query enforcement:

- max series
- max samples
- max log lines
- oversized payload truncation or rejection

Investigation-level budget:

```yaml
queryBudget:
  maxQueriesTotal: 12
  maxQueriesPerSource: 4
  maxConcurrentQueries: 2
  maxCumulativeDuration: 30s
  maxCumulativeResponseBytes: 4Mi
  resultLimits:
    metrics:
      maxSeries: 100
      maxSamples: 10000
    logs:
      maxStreams: 100
      maxEntries: 1000
    events:
      maxRecords: 500
```

Acceptance:

- `TemplatesOnly` query policy rejects unauthorized named templates before datasource execution
- query policy decisions are recorded with low-cardinality backend, decision, and reason labels
- policy records truncation reason
- evidence records `originalCount` and `retainedCount`
- query count, per-source count, cumulative duration, and cumulative response-byte budgets are enforced
- `maxConcurrentQueries` controls the datasource collection scheduler; unset or zero keeps the default sequential behavior
- metrics, logs, and events support adapter-native result-kind limits after backend response decode and before flattening/normalization
- exceeded result-kind limits retain bounded partial evidence and set truncation metadata instead of failing the whole investigation
- MVP favors predefined query templates or profiles with bounded parameters; backend syntax policy hardens rendered templates rather than accepting arbitrary user queries
- backend-specific syntax policy can restrict PromQL functions, subqueries, offsets, `@` modifiers, and native LogQL pipeline stages after template rendering
- tests cover query range rejection
- tests cover oversized response truncation
- docs do not imply every backend can know native result size before query execution
- implemented status: `spec.queryBudget` enforces pre-query max time range, total query count, per-source query count, negative limit validation, bounded datasource concurrency, cumulative datasource query duration, cumulative datasource response-byte limits, and metrics/logs/events result-kind limits. `DataSource.spec.queryPolicy.mode=TemplatesOnly` adds an opt-in pre-query template gate with allowed template names, max range, regex denial, target-scope checks, PromQL function allow/deny controls, PromQL subquery/offset/`@` controls, and LogQL pipeline stage allow/deny controls; empty policy and `LegacyUnrestricted` preserve compatibility with existing trusted query templates. Unset or zero `maxConcurrentQueries` keeps the default sequential collector; values above `1` enable bounded parallel datasource queries while preserving deterministic evidence ordering. Prometheus records native series/sample counts, Loki records native stream/entry counts, and Kubernetes event collection records raw event/condition counts before flattening or normalization. Exceeded native limits preserve bounded partial evidence with `truncationReason`, `limitDimension`, `limit`, `originalCount`, `retainedCount`, and `truncated` metadata.

## P0-11: Provider Data Boundary

Make hosted provider data transmission explicit and policy-controlled.

Target policy:

```yaml
spec:
  dataPolicy:
    allowExternalTransmission: true
    allowedEvidenceKinds:
      - MetricObservation
      - KubernetesEventObservation
    allowLogSamples: false
    maximumClassification: Internal
    deniedSensitivityTags:
      - CredentialLike
      - PersonalData
    requireRedaction: true
```

Data classification has two dimensions. Classification level is ordered:

```text
Public
Internal
Confidential
Restricted
```

Sensitivity tags are closed enums in the first v0.3 contract:

```text
CredentialLike
PersonalData
CustomerData
SourceCode
InfrastructureMetadata
SecuritySensitive
```

`CredentialLike` is a sensitivity tag, not a classification level. A piece of evidence can be `Restricted` and also tagged `CredentialLike`.

Provider egress order:

```text
raw evidence
-> normalization
-> redaction
-> classification
-> evidence-kind filtering
-> sensitivity tag evaluation
-> maximum classification evaluation
-> data policy evaluation
-> compaction
-> bundle digest
-> provider transmission
```

Propagation rules:

- raw evidence starts from datasource defaults, evidence-kind defaults, explicit policy, and content detection.
- effective evidence level is the most restrictive applicable level.
- normalized observations inherit the highest level and union of tags from their evidence.
- provider bundles inherit the highest level and union of tags from transmitted observations.
- provider results inherit at least the transmitted bundle classification.
- redaction does not automatically lower classification. Declassification is not supported in the first contract.

Acceptance:

- `ModelProvider.spec.dataPolicy` is defined
- hosted provider calls are blocked when external transmission is false
- heuristic-only mode remains fully usable
- log samples can be disabled independently from metrics and events
- evidence refs and normalized observations store computed classification summaries
- hosted provider calls are rejected when evidence exceeds `maximumClassification`
- hosted provider calls are rejected when evidence contains `deniedSensitivityTags`
- `requireRedaction` blocks hosted provider calls when transmitted evidence lacks redaction metadata
- egress audit records the decision, reason, provider type, evidence bundle digest, evidence kinds, sensitivity tags sent, whether log samples were included, maximum classification observed, maximum classification allowed, maximum classification sent, and classification policy version
- egress audit does not record full payloads
- docs state that read-only means read-only against user workloads, not zero data egress
- implemented status: hosted providers are blocked unless `spec.dataPolicy.allowExternalTransmission=true`; allowed hosted calls filter evidence kinds and log samples, evaluate ordered classification and denied sensitivity tags, require redaction when configured, and persist compact egress audit metadata. Rejected hosted transmission records a `Rejected` egress audit without calling the provider.

## P0-13: Required Evidence Profiles And NoIssueFound Gate

Prevent false confidence when evidence is incomplete.

Target profile:

```yaml
evidenceRequirements:
  profile: RolloutLatencyRegression
  required:
    - capability: prometheus.query
      observationType: LatencyRatio
    - capability: kubernetes.workloads.read
      observationType: RolloutTimeline
  optional:
    - capability: loki.query
      observationType: TimeoutPattern
```

Acceptance:

- `NoIssueFound` is only allowed when required evidence is complete
- incomplete required evidence produces `Inconclusive`
- `NoIssueFound` means required evidence shows the target is normal
- `Inconclusive` means FluxAgent cannot confirm a root cause or evidence is insufficient
- inability to find data is not enough to produce `NoIssueFound`
- P0-1 legal status combinations reference this gate
- profiles are type-specific
- tests cover ImagePullBackOff and LatencyRegression with different required sources
- implemented status: `spec.evidenceRequirements.profile` supports required evidence profiles for `ImagePullBackOff`, `CrashLoopBackOff`, `OOMKilled`, `LatencyRegression`, and `RolloutLatencyRegression`; missing required evidence completes the workflow as `Inconclusive` before provider execution, while complete normal evidence completes as `NoIssueFound` without calling the provider.

- implemented status: `internal/rcametrics` defines the first metric set and guards the allowed label contract against high-cardinality fields.
